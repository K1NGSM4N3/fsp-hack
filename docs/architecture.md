## 1. Принципы

1. **Механики важнее инфраструктуры.** 60 % оценки — подбор (35 %) и тестирование (25 %), инфраструктура — 7 %. Инфра скучная и надёжная, время уходит в механики и их валидацию.
2. **Категория — только из теста.** Самоописание и резюме влияют на подбор как вторичный сигнал, но никогда не определяют категорию (`M-1`).
3. **Всё объяснимо.** Каждый балл ранжирования раскладывается на понятные причины, которые видит работодатель (`M-3`).
4. **Валидируем тот же код, что работает в проде.** Симулятор валидации вызывает крейты `assessment` и `matching` напрямую, без переписывания логики.
5. **Приватность по умолчанию.** Работодатель видит анонимную карточку; контакты физически не попадают в его DTO, пока нет основания (`V-2`, `E-7`).

## 5. Механика тестирования (`T-2…T-6`)

### 5.1. Идея

Вместо единого набора заданий и вместо LLM-генерации «под каждого» — **параметрические шаблоны заданий, откалиброванные по IRT, в адаптивном тесте (CAT)**.

1. **Шаблон задания** (item model) — генератор, который по `seed` выдаёт конкретный экземпляр: другие числа, код, имена, порядок вариантов, набор дистракторов. Правильный ответ **вычисляется** генератором (например, порядок вывода в event loop считается мини-симулятором), а не хранится.
   - *Радикалы* — параметры, меняющие сложность (число асинхронных задач, глубина вложенности циклов). Каждому уровню радикалов соответствует своя откалиброванная сложность.
   - *Инциденталы* — параметры, не меняющие сложность (числа, имена, порядок вариантов).
2. **IRT-калибровка.** У каждого (шаблон, уровень радикалов) есть параметры `a` (дискриминативность), `b` (сложность), `c` (угадывание = 1/k для выбора из k, 0 для числового ответа). Способность кандидата `θ` измеряется на **общей шкале специализации**, поэтому разные кандидаты получают разные задания, а результаты сопоставимы.
3. **Адаптивный тест (CAT).** Каждое следующее задание выбирается под текущую оценку `θ` с максимумом информации Фишера, с балансом тем и случайным выбором среди лучших (контроль экспозиции).
4. **Решение о грейде** — классификационный тест относительно порога заявленного грейда: тест останавливается, когда ясно, выше кандидат порога или ниже.

### 5.2. Почему это устойчиво к утечкам

| Что утекло | Что получает утечка |
|---|---|
| Конкретный экземпляр задания с ответом | Почти ничего: следующий кандидат получит другой `seed` — другой код и другой ответ |
| Шаблон («тут спрашивают порядок event loop») | Знание того, как решать такой класс задач — это и есть навык, который мы измеряем |
| Весь банк шаблонов | CAT выбирает 8–20 заданий из 15–24 шаблонов специализации по теме и уровню; ответы всё равно надо вычислить, а на каждое задание действует лимит времени |

Дополнительно:
- **лимит времени на задание** (таймаут = неверный ответ) — нет времени гуглить;
- **person-fit** (статистика `l_z`): «верно на трудных, неверно на лёгких» → флаг аномалии; вместе с событиями прокторинга (уход со вкладки, вставка текста) результат помечается «требует подтверждения» (§5.6);
- **контроль экспозиции**: случайный выбор среди пяти самых информативных заданий (randomesque). Потолка частоты показа шаблона нет и при таком банке он мало что даёт: тест показывает большую часть шаблонов специализации (по валидации — медиана 83 % сессий), поэтому защита держится на неповторимости экземпляров, а не на редкости шаблона.

**Роль LLM:** только офлайн — предложить *новый шаблон*, который проходит ревью и pretest-калибровку (показывается без влияния на оценку), прежде чем попасть в боевой банк. Сопоставимость сложности гарантирует калибровка, а не генератор.

### 5.3. Параметры алгоритма

| Параметр | Значение |
|---|---|
| Модель | 3PL (D = 1,702) с фиксированным `c`: 1/k для выбора одного из k, 1/31 для «выберите все верные» из пяти, 0 для ввода |
| Оценка `θ` | EAP, квадратура 81 точка на [-4, 4] |
| Априорное распределение | N(μ, 1), μ = порог заявленного грейда (стартуем с «середины» заявки) |
| Пороги грейдов (шкала θ) | junior ≥ −1.0, middle ≥ 0.0, senior ≥ 1.0 |
| Длина теста | min 8, max 20 заданий |
| Остановка | 95 % интервал апостериорного распределения не содержит порог заявленного грейда, либо достигнут max, либо кончились шаблоны специализации |
| Решение | `θ̂ ≥ порог` → пройден |
| «Уверенно справился» | P(θ ≥ порог следующего грейда) ≥ 0.9 или измеренный грейд выше заявленного → предложить дотест на грейд выше |
| Баланс тем | мягкий: информация задания × (1 + недобор темы до целевой доли max/число тем); стек из опроса или потребности — × 1,5 шаблонам с совпадающими навыками; шаблон в сессии не повторяется |
| Время | лимит на уровень шаблона (60–180 с) + 5 с на сеть; просрочка — неверный ответ; фиксируется время ответа |

### 5.4. Правила смены грейда (`T-5`, `T-6`)

Правила — чистый модуль `assessment::policy` (`GradePolicy`), время приходит параметром.

- **Первичное размещение:** кандидат выбирает грейд → тест. Не прошёл → сразу может пройти на грейд ниже (это ещё размещение, а не смена), и так вплоть до Junior. Тот же или более высокий грейд — через 30 дней. Не прошёл junior → категории нет, пересдача через 30 дней.
- **Неудачная попытка закрывает свой грейд на 30 дней** — для любого вида попытки: повтора, дотеста, повышения, понижения. Неудачная — это проваленная или брошенная (ниже).
- Прошёл уверенно → предлагается дотест на грейд выше (один раз в рамках размещения). Если этот грейд кандидат провалил или бросил меньше 30 дней назад, дотест откроется, когда пройдут эти 30 дней: провалил Middle, уверенно сдал Junior → дотест на Middle через 30 дней после провала, не сразу. До этого он показывается с датой (`locked` в `GET /candidate/category` и в результате теста).
- **После присвоения:** смена грейда (вверх или вниз) — **не чаще раза в 90 дней** (`GRADE_CHANGE_COOLDOWN_DAYS`).
- Неудачная попытка повышения **не понижает** грейд; следующая попытка — через 30 дней, но не раньше конца 90-дневного окна от присвоения. Если действуют несколько окон, API называет дату, когда закроется последнее из них, — ту, когда попытка правда станет доступна.
- **Брошенный тест.** Сессия, в которой 30 минут после дедлайна текущего задания нет ответа (`assessment::ABANDON_AFTER_SECS`), закрывается как `expired` и во всех правилах выше считается неудачной попыткой на свой грейд. Момент попытки — «дедлайн + 30 минут», а не время, когда это заметили: закрытие ленивое (при старте теста, чтении истории, категории и текущего задания, при ответе), и окно в 30 дней не зависит от того, когда кандидат вернулся. Ответ после этого срока — 409 `assessment_finished`. Иначе можно было бы бросать неудачно идущий тест и пересдавать сразу.
- Состояния «сбой на стороне платформы» у сессии нет: тест не ждёт ни камеру, ни загрузку записи, а прерванная видеозапись («запись прервалась», §5.6) только помечает результат — брошенным тест она не делает.
- Вся история (опросы, сессии, ответы, решения) хранится и показывается кандидату (`C-4`).

### 5.5. Демонстрация на вакансиях (`T-4`)

В seed-данных лежат несколько описаний вакансий/потребностей: у демо-работодателя `employer@demo.fsp` — шесть, по одной на специализацию (отдельная функция `seed::demo`, без случайности; `created_at` разнесены на час, порядок списка стабилен, первой идёт Go-потребность). Для каждой система показывает: какие специализация и грейд извлечены, какие темы и навыки покрывает тест, пример сгенерированных экземпляров заданий с разными `seed`. Регулярные задания работодателя (`T-8`) привязываются к категории и навыкам потребности.

### 5.6. Видеозапись и журнал событий (прокторинг)

Наше дополнение, ТЗ его не требует. Задача — подтвердить, что тест пройден самостоятельно, не ломая приватность и не мешая отвечать. Флаг `PROCTORING=optional|off` (по умолчанию `optional`; при `off` шага нет, запись и события не ведутся).

1. **Шаг перед тестом.** Предпросмотр камеры, три коротких пункта (что записываем, кто увидит, сколько храним) и галочка согласия — отдельный версионированный документ `proctoring_video` в механизме согласий (`required_for` пустой: при регистрации не спрашивается). Кнопки «Начать с видеозаписью» и «Продолжить без камеры». Выбор уходит в `POST /candidate/assessments` полем `proctoring`; без камеры тест идёт так же, у результата отметка «без видеозаписи».
2. **Во время теста** браузер пишет только видео (MediaRecorder, ~320×240, 15 к/с, VP8 ~100 кбит/с) и каждые 10 с отправляет фрагмент `PUT …/proctoring/chunks/{seq}`. Фрагменты — куски одного WebM-потока (заголовок только в первом), поэтому сервер принимает их строго по порядку: на диске всегда непрерывный префикс, который проигрывается склейкой. Параллельно батчами (до 50) уходят события: вкладка скрыта, окно потеряло фокус, выход из полноэкранного режима (полный экран предлагаем, не навязываем), вставка текста в поле ответа, камера отключилась, запись остановилась. События пишутся и без камеры. Индикатор «Идёт запись» с миниатюрой камеры виден всё время записи.
3. **Ничего не блокирует ответ.** Загрузка — фоновая очередь с повторами; любая ошибка (нет камеры, сеть, перезагрузка страницы, уход со страницы теста) превращается в «запись прервалась», тест продолжается.
4. **Хвост.** Последний фрагмент рекордер отдаёт после `stop()`, то есть после последнего ответа. Поэтому фрагменты и события принимаются, пока сессия идёт, и ещё 60 с после её завершения; дальше — 409.
5. **Сводка** (чистая функция `assessment::proctoring`): `declined` — камеру не включали; `interrupted` — камеру выбрали, но была техническая ошибка или не пришло ни одного фрагмента; `recorded` — иначе; `recording` — пока тест идёт. Плюс число событий по типам. Считается из сохранённых фактов при каждом чтении — так в неё попадают фрагмент и события, пришедшие в «хвосте».
6. **«Требует подтверждения».** Флаг person-fit (`l_z < −2`) **и** хотя бы одно поведенческое событие (уход, вставка, выход из полного экрана). По отдельности это не улика: под моделью `l_z ≈ N(0, 1)`, порог −2 срабатывает примерно у 2 % честных кандидатов, а переключение вкладки — обычное дело. Сессии без данных прокторинга сохраняют прежнее правило (только person-fit). Отметка ничего не меняет в грейде автоматически — её видят кандидат и модератор, который принимает решение (§5.7).

| Кто | Что видит |
|---|---|
| Кандидат | Сводку в результате и в истории тестов, свою запись (`GET …/proctoring/recording`), дату удаления, и ровно ту отметку, которую видят работодатели |
| Работодатель | Только отметку в анонимной карточке и профиле: «Тест с видеозаписью» / «Тест без видеозаписи» / «Запись прервалась», «Есть замечания: 2 ухода со вкладки» и «Результат подтверждён», если модератор подтвердил тест (§5.7). В DTO `ProctoringBadge` нет id сессии и ссылки; эндпоинты записи для него — 403 |
| Модератор | Журнал событий, ответы по сложности и запись любой сессии для разбора спора (§5.7); каждый просмотр записи — строка журнала аудита до отправки видео, кандидат видит даты просмотров |

Хранение и удаление — §9.2.

### 5.7. Разбор спорных результатов (модерация)

Наше дополнение. Роль `admin` в интерфейсе называется «Модератор»: регистрацией она не выдаётся (422), в демо-данных — `moderator@demo.fsp` (отдельная функция сида). Кабинет `/admin`, API — `/api/v1/admin/*`, тег «Модерация» (docs/api.md).

**Очередь** (`GET /admin/proctoring`): завершённые тесты, самые старые сверху, курсор по `(finished_at, id)`. Фильтры: «Требуют подтверждения» — правило §5.6 (person-fit и поведенческое событие; у теста без данных прокторинга — один person-fit), «С замечаниями» — уходы со вкладки, вставка текста, выход из полноэкранного режима, «Все с видеозаписью». В первых двух — только тесты без решения. В SQL правило «требует подтверждения» повторено ради курсора; тест сверяет очередь с флагом карточки.

**Карточка теста** — всё, что нужно для решения, и ничего сверх: категория и грейд, анонимный код «K-XXXXXX», θ̂ с 95 % интервалом и порогом, что этот тест сейчас делает с категорией, person-fit `l_z` с разбором (сколько заданий сложнее уровня кандидата решено и сколько лёгких — нет) и точечной диаграммой ответов по сложности (параметр `b`), видео и лента «задания + события»: у каждого ухода со вкладки или вставки — задание, которое было на экране (номер из браузера, а если его нет — по времени показа и ответа). Текст экземпляров и ответы не показываются. **ФИО, контактов и email кандидата нет**: чтобы решить, сам ли человек проходил тест, личность не нужна — нужны ответы, события и запись (минимизация, ст. 5 ч. 5 152-ФЗ). Видео — уже персональные данные, поэтому плеер не грузится, пока модератор не нажмёт «Открыть запись», а каждый просмотр пишется в журнал (§9.2).

**Решение** — одно на тест, окончательное, с обязательным комментарием до 2000 символов (его читает кандидат). Транзакция: блокировка строки сессии, `session_reviews`, изменения грейда, строка `moderation_actions`; не записалась строка журнала — не случилось и решение.

| Решение | Что меняется |
|---|---|
| «Подтвердить результат» | Отметка «требует подтверждения» снимается у кандидата и в очереди. В карточке работодателя `result_confirmed = true` — «Результат подтверждён», пока категория идёт от этого теста |
| «Аннулировать результат» | `grade_assignments.annulled_at` у присвоения этого теста (строка остаётся в истории). Категория в `candidates` пересчитывается по последнему действующему присвоению — или снимается. Навыки с источником `test`, которые подтвердил только этот тест, теряют этот источник (подтверждённые и другим действующим тестом остаются). Сброс кеша пула (§12.2) |
| «Назначить пересдачу с видеозаписью» | То же, что аннулирование, плюс немедленная пересдача и требование камеры |

**Политика грейда** (`assessment::policy`, модульные тесты рядом):

- Аннулированная попытка — `Outcome::Annulled`: никогда не присваивает, неудачна на свой грейд, а её момент `at` — **решение модератора**, а не сам тест. Следствия: текущий грейд — последнее неаннулированное присвоение, и 90-дневное окно смены считается от *его* даты, окно аннулированного присвоения исчезает (Junior с T0, повышение до Middle в T0 + 100 дн., аннулировано в T0 + 101 дн. → снова Junior, а Middle откроется через 30 дней после решения, не в T0 + 190); грейд аннулированного теста закрыт на 30 дней от решения, как после провала, — медленный разбор не дарит немедленную пересдачу; после аннулированного первичного теста шаг вниз доступен сразу, как после провала; аннулирование присвоения, уже заменённого более поздним, текущий грейд не меняет.
- Пересдача — `Outcome::RetestOrdered`: всё то же, но `GradePolicy::ordered_retest` открывает ту же попытку (тот же грейд и вид — первичный тест, дотест, повышение) сразу и вне всех окон, пока после решения в специализации не было других попыток. Кандидат выбрал другой тест — пересдача сгорает, попытка дальше считается аннулированной. В `GET /candidate/category` такое предложение помечено `ordered_retest` и подписано «Пересдача с видеозаписью».
- Камера — `policy::camera_required`: после назначения пересдачи тест **на этот грейд и выше** начинается только с `proctoring.camera = true`, иначе 409 `camera_required`; требование действует, пока не завершится (сдан или не сдан) тест с камерой на этом грейде или выше, начатый после решения. Брошенный тест требования не снимает, попытка «нацелиться на грейд выше» его не обходит, тест ниже — свободен. Шаг с камерой прячет «Продолжить без камеры». При `PROCTORING=off` пересдачу не назначить (409 `proctoring_off`).

**Кто что видит.** Кандидат — решение и комментарий у теста в истории, пометку «аннулировано» у присвоения в истории категории, даты просмотров записи модератором у теста (`recording_views`) и всё это в выгрузке ст. 14. Работодатель — только обновлённую карточку: категорию (прежнюю или никакую) и «Результат подтверждён»; комментарий, решение и видео к нему не попадают.

## 6. Механика подбора и выхода на контакт (`M-1…M-4`, `E-2…E-5`)

### 6.1. Сценарий

1. **Работодатель описывает потребность**: специализация, грейды, обязательные и желательные навыки (можно свободным текстом — навыки извлекаются словарём), чем занимается команда, формат, город, вилка «от–до».
2. **Система показывает рекомендованные категории** (карточки: сколько кандидатов, сколько с ФСП, медианные ожидания по зарплате, совпадение со стеком) и **подборку** конкретных кандидатов.
3. **Анонимные карточки**: категория, результат теста (положение внутри диапазона грейда), подтверждённые навыки, ФСП, опыт, ожидания — без имени и контактов («слепой» отбор). Имя кандидат может открыть в настройках приватности.
4. **Объяснение попадания**: топ-причины и пробелы — «4 из 5 обязательных навыков» и отдельно «Нет обязательного навыка: Kubernetes», «Результат теста выше 71 % диапазона грейда Middle», «призёр всероссийских соревнований ФСП по продуктовому программированию, 2025», «ожидания пересекаются с вилкой».
5. **Уточнение без потери подборки** (`M-4`): подборка хранится в БД; уточнение фильтров пересчитывает её, но закреплённые и скрытые кандидаты сохраняются, новые помечаются.
6. **Приглашение**: описание, вилка (обязательно), формат, компания и способ связи; можно без вакансии (`E-5`). Можно приложить короткое задание.
7. **Кандидат видит условия до общения** и принимает или отклоняет (с причиной: зарплата / стек / формат / компания / не ищу).
8. **После принятия** работодатель получает контакты (с записью в журнал доступа), кандидат — контакт компании (виден сразу).

### 6.2. Чем отличается от прямого отклика

- Инициатива у работодателя, который ищет **по подтверждённым категориям**, а не по ключевым словам резюме.
- Условия (вилка) — в первом же сообщении; кандидат решает, тратить ли время.
- **Квота приглашений**: от 5 до 30 приглашений компании за 7 дней по уровню доверия (§11.1; новая компания — 10) и одно активное приглашение на пару «компания–кандидат» — работодатель выбирает точечно, кандидат не тонет в спаме. Квота — также элемент антифейка.
- **Срок жизни приглашения** 14 дней → `expired`. Доля приглашений, на которые кандидаты ответили (response rate), видна работодателю в статистике приглашений и учитывается в уровне доверия (§11.1); кандидату она пока не показывается.
- **Обратная связь обеим сторонам**: работодатель видит агрегированные причины отказов («60 % отказов — зарплата»); кандидат видит анонимную статистику спроса в своей категории (сколько компаний смотрели, медианная вилка приглашений) — мотивация пройти тест выше.
- Классический отклик на вакансию остаётся как дополнительный путь (`C-6`, `E-6`): контакты раскрываются и при собственном отклике.

### 6.3. Отбор и скоринг

**Жёсткие фильтры:** кандидат видим в поиске и открыт к предложениям; есть действующая категория по нужной специализации; грейд из запрошенных (или соседний, если работодатель разрешил); формат и город совместимы.

**Скоринг** — взвешенная сумма признаков из [0, 1], итог 0–100:

| Признак | Вес | Как считается |
|---|---|---|
| `must` — обязательные навыки | 0.41 | Σ по обязательным навыкам max(близость × уверенность) / их число; уверенность: подтверждён тестом или ФСП (§7.4) — 1.0, из резюме — 0.7, только заявлен — 0.5. У навыка из нескольких источников берётся самый надёжный: тест, ФСП, резюме, заявлен |
| `test` — сила теста | 0.10 | Нормированное положение θ внутри диапазона грейда (у senior верх диапазона — θ = 2,5) |
| `grade` — совпадение грейда | 0.15 | 1.0 точное, 0.6 на грейд выше, 0.5 на грейд ниже |
| `fsp` — достижения ФСП | 0.10 | ФСП-скор (§7.3) |
| `nice` — желательные навыки | 0.08 | Как `must` |
| `salary` — пересечение вилок | 0.07 | 1.0 если ожидания ≤ верх вилки; линейно падает до 0 при превышении на 30 %; ожидания не указаны — нейтральные 0.7 |
| `fresh` — актуальность | 0.05 | exp(−дней с последней активности / 60): тест, регулярное задание, сохранение профиля, опрос, синхронизация ФСП, отклик, ответ на приглашение |
| `text` — близость описаний | 0.04 | По смыслу: косинус эмбеддингов текста потребности (название + описание) и профиля (роли, «о себе», должности и описания мест работы), линейно между калибровочными 0,88 и 0,918 → 0..1 (§6.4). Нет вектора у потребности или у кандидата — по ключевым словам: `ts_rank_cd` описания потребности и «о себе», нормированный на лучшего. Если у потребности заданы отрасли — 0.6 · текст + 0.4 · совпадение отраслей (без описания — только отрасли) |

**Сила профиля внутри категории** (`T-7`, `M-2`, просмотр категории без потребности): `0.6·test + 0.25·fsp + 0.15·fresh`.

Веса лежат в одном месте (`matching::Weights`) и подобраны на валидации (§8.2, `docs/validation/matching.md`): исходные 0.30 / 0.25 / 0.10 для must / test / grade проигрывали по nDCG@10 (0.77 против 0.84). Вес близости описаний перебирался от 0.04 до 0.20: на обучающих потребностях больше 0.04 только хуже, поэтому он остался 0.04. Категория из теста уже работает жёстким фильтром и признаком грейда, поэтому положение θ внутри грейда — уточняющий сигнал, а реальное покрытие стека разделяет кандидатов лучше всего. Признаки без входных данных (нет желательных навыков, нет описания и отраслей) выпадают, веса перенормируются; зарплата не выпадает — неизвестные ожидания дают нейтральные 0.7. Каждый признак отдаёт своё человекочитаемое объяснение.

### 6.4. Эмбеддинги (смысловая близость текстов)

Где работают: признак `text` подбора (§6.3), отметка «пересказ чужой вакансии» антифейка (§11.1), «Похожие вакансии» (`GET /vacancies/{id}/similar`), проверка на своих данных (`POST /eval/pairs`, CLI `validate pairs`). Без эмбеддингов (`EMBEDDINGS=off`, сервис остановлен, вектор ещё не посчитан) каждое место возвращается к прежнему поведению: ключевые слова, общие навыки, только MinHash.

- **Модель** — `intfloat/multilingual-e5-small` (MIT, 118 млн параметров, 384 измерения, RU + EN), ревизия `614241f…`; как в карточке модели: среднее по токенам под маской внимания, L2-нормировка, префиксы `query: ` (потребность, вакансия — их сравнивают друг с другом) и `passage: ` (профиль). Сравнивалась с `cointegrated/rubert-tiny2` (MIT, 29 млн, 312 измерений; по карточке — вектор `[CLS]`): на длинных текстах профилей её косинус почти не связан с реальными навыками (корреляция −0,08 против 0,30 у e5) и идёт за длиной текста, пересказы вакансий она отделяет хуже (ROC AUC 0,948 против 0,978). Выбор и цифры — `docs/validation/embeddings.md`, docs/solution.md §5.6.
- **Рантайм** — крейт `embedder`: candle (BERT-энкодер на CPU, без C-зависимостей) и `tokenizers` без onig и esaxx (`fancy-regex`). Две экономии памяти. Матрица эмбеддингов токенов (250 037 × 384, 82 % весов) не копируется в память: строки читаются из отображённого файла весов, а прочитанные страницы — чистый файловый кеш, который ядро выгружает под лимитом. Словарь Unigram (250 тыс. кусков) держит не байтовый trie библиотеки с хэш-таблицей в каждом узле (~390 МБ), а одна таблица «кусок → id» (`embedder::unigram`) с тем же поиском лучшего разбиения; равенство id библиотечным проверено на 3 000 случайных строк. Итог — ~110–130 МБ после загрузки и до ~250 МБ под нагрузкой (своя память — ~180 МБ, остальное — страницы файла весов) вместо ~600 МБ одной только загрузки. Корректность модели — золотые тесты против `transformers` (id токенов и первые компоненты векторов, `cargo test -p embedder -- --ignored` после `make model`).
- **Сервис** — `POST /embed {texts[], kind: query|passage}` → `{model, dim, vectors}`; до 64 текстов по 8 000 символов (422 сверх), тело до 4 МиБ. Тексты запроса идут проходами по длине (≤ 32 текстов и ≤ 1 024 токенов с паддингом на проход, обрезка до 512 токенов), поэтому вектор текста не зависит от соседей по запросу. Одновременно идёт `EMBEDDER_CONCURRENCY` проходов (1): candle и так занимает все `RAYON_NUM_THREADS` потоков, а запрос, ждущий дольше `EMBEDDER_QUEUE_WAIT_MS`, получает 503. `GET /healthz` — модель, `GET /metrics` — `embedder_requests_total{result}`, `embedder_texts_total`, `embedder_inference_seconds`. Веса скачиваются при сборке образа с Hugging Face по закреплённой ревизии и проверяются по sha256 (`crates/embedder/fetch-model.sh`); без сети — `EMBEDDER_FETCH=0` и каталог с весами, смонтированный в `EMBEDDER_MODEL_DIR`.
- **Очередь** (миграция 0017). Триггеры на `candidates` (`about`, `roles`, `experience`), `hiring_needs` (`title`, `description`) и `vacancies` (`title`, `description`, `status`) кладут сущность в `embedding_jobs` в той же транзакции, что и запись текста: ни один путь записи — форма, импорт из ATS, сид — не может её забыть, а запрос никогда не ждёт модель. Повторная запись, пока строка ждёт, только сдвигает `enqueued_at`. Воркер API (`embeddings::worker`, по одному на реплику) берёт до 32 строк с `FOR UPDATE SKIP LOCKED` и арендой 120 с, собирает тексты (`matching::semantic::{candidate_text, posting_text}`), отправляет в модель только те, у которых изменился хэш текста или модель, пишет векторы и удаляет строку, только если `enqueued_at` не сдвинулся. Сбой эмбеддера — строка ждёт 5 с, 30 с, 2 мин, дальше раз в 10 мин; смена модели (другой `name@revision` в ответе) ставит в очередь все векторы прежней. Векторы профилей и потребностей сбрасывают поколение кеша (§12.2). Метрики — `embedding_jobs_pending`, `embeddings_total{kind, result}`.
- **Подбор.** Снимок пула грузит векторы профилей специализации и хранит их квантованными в `i8` с обратной нормой на строку (`matching::semantic::Embeddings`: 388 байт вместо 1 536 на профиль), отдельно от горячих записей скоринга. Вектор потребности читается из базы раз на поколение и лежит в памяти процесса (1 024 слота с прямым отображением, как компания работодателя): лишний запрос к базе на каждый поиск под потребность стоил 13–21 % пропускной способности; близость по смыслу всех кандидатов снимка к ней считается один раз и кешируется в слотах снимка, как ранги `ts_rank_cd`; если векторы есть у всех кандидатов, `ts_rank_cd` не считается вовсе. Калибровка `Calibration { floor, ceil, paraphrase }` своя у каждой модели (`matching::semantic::calibration`; модель без калибровки не используется): `floor` и `ceil` — 10-й и 99-й перцентили косинусов потребностей обучающей выборки с профилями своей специализации. Объяснение — «Близость описаний по смыслу: 72 %», причина «Опыт близок к задаче по смыслу» — от 0,6; без вектора — «Близость описаний по ключевым словам: 40 %».
- **Антифейк.** Опубликованная вакансия после появления вектора сравнивается с опубликованными за 90 дней вакансиями других компаний (HNSW по `vacancy_embeddings`; `hnsw.iterative_scan = relaxed_order`, чтобы фильтры не съедали соседей): косинус ≥ 0,953 — отметка `paraphrase_of_other` (§11.1). Порог — без ложных срабатываний на калибровочном наборе (`docs/validation/paraphrase.md`): между самой похожей «не копией» (0,9527) и ближайшим пересказом выше неё (0,954). Если MinHash уже нашёл дословную копию, второй отметки нет. Отметку пересказа пишет только воркер, проверка при сохранении — свои (MinHash, вилка); каждый пишет свою половину `trust_flags` одним `UPDATE`, который читает текущие отметки строки под её блокировкой.
- **«Похожие вакансии».** Ближайшие опубликованные по косинусу (втрое больше показанных), сначала той же специализации, внутри — по близости; без вектора — той же специализации по доле общих навыков. Ответ говорит, как найдены соседи (`method`).

## 7. ФСП (`F-1…F-4`)

### 7.1. Привязка ФСП ID

```
Кандидат → «Привязать ФСП ID» → api: /fsp/link/start (state, PKCE verifier и nonce — в oidc_states, 10 минут)
   → Keycloak realm fsp: логин участника ФСП → redirect с code
   → api: /fsp/link/callback — обмен code на токены, проверка id_token (JWKS, iss, aud, nonce), claim fsp_id
   → api → реестр ФСП: GET /participants/{fsp_id}/achievements (Bearer: сейчас статический FSP_REGISTRY_TOKEN,
     с настоящим реестром — токен client credentials realm fsp)
   → сохраняем снимок достижений + время синхронизации → пересчёт ФСП-скора
```

- `fsp_id` — атрибут пользователя Keycloak, отдаётся claim'ом через protocol mapper.
- Один `fsp_id` можно привязать только к одному кандидату.
- Отвязка удаляет снимок достижений и навыки, подтверждённые ФСП (§7.4). Синхронизация — при привязке, вручную (`POST /fsp/sync`) и по событию реестра (push, ниже); реестр недоступен — привязка сохраняется, снимок прежний (при новой привязке — пустой), `POST /fsp/sync` без настроенного реестра — 503 `fsp_registry_disabled`. Фоновая сверка раз в сутки — страховка на случай потерянных событий, после MVP.
- Для локальной разработки без Docker — `FSP_DEV_LINK=true` разрешает привязку введённым `fsp_id` без Keycloak. В проде выключено.
- Позже наша платформа может сама принимать вход через ФСП ID (Keycloak identity brokering).

**Push от реестра** (`POST /api/v1/fsp/registry/events`). Опрос по кнопке узнаёт о новом результате, только когда кандидат сам зайдёт в настройки; реестр же знает о нём первым. Поэтому реестр сообщает об изменении, а данные платформа по-прежнему забирает сама — тем же запросом, что и при привязке:

```
Реестр ФСП ── POST /fsp/registry/events {event_id, type: achievements.changed, fsp_id, occurred_at}
   │          FSP-Signature: t=<unix>,v1=hex(HMAC-SHA256(FSP_REGISTRY_WEBHOOK_SECRET, t + "." + тело))
   ▼
api: лимит 300/мин с адреса → подпись и метка (±5 мин) → разбор тела
   │  fsp_id не привязан — 202, ничего не пишем; event_id уже был — 202
   ▼
api → реестр: GET /participants/{fsp_id}/achievements          (вне транзакции)
   │  реестр не ответил — 502: событие не записано, реестр доставит его снова
   ▼
одна транзакция: fsp_registry_events (event_id) → блокировка fsp_links → снимок и навыки `fsp`
                 → если снимок изменился: уведомление `fsp_achievements`
   ▼
после коммита: сброс поколения кеша пула (§12.2) — только если что-то изменилось
```

- **Почему событие без данных.** Достижения — персональные данные участника; в событии только идентификаторы, данные берутся по токену реестра. Подделанное или повторённое событие ничего не меняет: худшее, что оно может сделать, — заставить нас лишний раз прочитать реестр, и это ограничено лимитом.
- **Подпись** — та же схема, что у наших вебхуков ATS (§11.2, `integrations::signature`): метка внутри MAC, окно 5 минут, сравнение без раннего выхода. Без `FSP_REGISTRY_WEBHOOK_SECRET` метод отвечает 503 — работает только pull.
- **Ровно один раз.** `event_id` — первичный ключ `fsp_registry_events`, строка пишется первой в транзакции: повтор, пришедший одновременно, ждёт коммита первого и получает 202 без изменений. Реестр не ответил — транзакции не было, повтор события отработает полностью. Строки живут 30 дней и уходят вместе с привязкой.
- **Ничего о чужих.** Ответ — 202 без тела для любого принятого события: применено, ничего не изменило, уже было или `fsp_id` у нас не привязан. О незнакомом участнике ничего не сохраняется.
- **Та же синхронизация.** Снимок и навыки из ФСП пишутся тем же кодом, что `POST /fsp/sync`, под блокировкой строки привязки — две синхронизации одного кандидата идут по очереди. Отличие одно: событие реестра не обновляет «последнюю активность» кандидата — он ничего не делал.
- **Уведомление** «Новые достижения ФСП в профиле» (или «Данные ФСП в профиле обновились», если записи только убраны) — в той же транзакции; изменения сравниваются по `id` записей реестра.

### 7.2. Модель достижений

| Поле | Значения |
|---|---|
| `kind` | `rank` (разряд), `competition` (соревнование) |
| `discipline` | `algorithmic`, `product`, `security`, `ai`, `robotics`, `uav` — дисциплины спортивного программирования |
| `rank` | `youth`, `third`, `second`, `first`, `cms` (КМС), `ms` (МС) |
| `event_level` | `regional`, `interregional`, `national`, `international` |
| `place` | 1, 2, 3, `finalist`, `participant` |
| прочее | название события, команда, роль, дата, ссылка на протокол |

### 7.3. ФСП-скор

Вклад каждого достижения: `v = вес_уровня × вес_места × релевантность(дисциплина, специализация) × затухание`.

- Уровень: regional 0.3, interregional 0.5, national 0.8, international 1.0.
- Место: 1 → 1.0, 2 → 0.8, 3 → 0.7, finalist → 0.4, participant → 0.15.
- Разряд вместо уровня × места: МС 1.0, КМС 0.8, I 0.6, II 0.4, III 0.25, юношеский 0.1.
- Релевантность: матрица дисциплина × специализация (например, `security` → security 1.0, devops 0.6, backend 0.5; `product` → backend/frontend 1.0).
- Затухание: период полураспада 2 года.
- Итог: `fsp = 1 − Π(1 − vᵢ)` — растёт с каждым достижением, насыщается к 1, не может доминировать (вес в подборе 0.10).

**Членство в ФСП** не учитывается (уточнение организаторов: оно платное и для разряда не нужно): такого поля нет ни в анкете, ни в модели достижений, и привязанный ФСП ID без разрядов и результатов скор не меняет (`has_fsp` — это наличие достижений, а не привязки).

**Кандидат без ФСП** (`F-3`): `fsp = 0`, никаких штрафов и «0 достижений» красным — в интерфейсе нейтральное «Нет данных ФСП». В фильтре «есть достижения ФСП» он просто не попадает.

### 7.4. Навыки, подтверждённые ФСП

Результат ФСП подтверждает навыки словаря с источником `fsp` — с доверием 1,0, как тест (§6.3). Правило — чистая функция `matching::confirmed_skills` поверх таблицы `Discipline::skills`. Таблица намеренно узкая: реестр хранит дисциплину и результат, но не стек команды и не роль участника, поэтому засчитывается только то, что упражняет любое соревнование дисциплины.

| Дисциплина | Навыки | Почему |
|---|---|---|
| Алгоритмическое | `algorithms` (Алгоритмы), `data_structures` (Структуры данных) | задачи решаются алгоритмами и структурами данных |
| Системы ИБ | `pentest` | CTF — поиск и эксплуатация уязвимостей |
| Системы ИИ | `machine_learning`, `ml_metrics` | модель на скрытых данных, место — по метрике качества |
| Продуктовое | — | стек продукта в реестре не указан; результат и так весит в ФСП-скоре (релевантность для backend и frontend — 1,0) |
| Робототехника, БАС | — | в словаре нет навыков встраиваемых систем |

- **Только результат:** любой разряд (их присваивают за результаты) или место 1–3 и выход в финал. Участие ничего не подтверждает.
- **Жизненный цикл.** Навыки пишутся в той же транзакции, что и снимок достижений: привязка (пока реестр не ответил — пусто), синхронизация, отвязка (удаляются). Строки других источников не трогаются — понижать нечего: у навыка, подтверждённого и тестом, и ФСП, остаются обе строки, а в объяснении назван тест. При старте API навыки сверяются со снимками (`skills::backfill_fsp_skills`) — для привязок, сделанных до этого правила, и после смены таблицы; демо-данные пишут их тем же кодом. Каждое изменение сбрасывает поколение кеша пула (§12.2).
- **Скрытие.** При `show_fsp = false` эти навыки, как и сами достижения, не попадают ни в пул поиска, ни в карточку работодателя (условие в SQL `db::pool`) — значит, не участвуют ни в ранжировании, ни в объяснении. Кандидат видит их в своём профиле всегда.
- **Объяснение** называет их отдельно: причина «Алгоритмы — подтверждено ФСП», тот же хвост у текста признака навыков, источник «ФСП» в разборе навыков.
- **Проверка на своих данных** (`matching::pairs`, §8.2) выводит навыки из `fsp_achievements` тем же правилом — только для нашего ранжирования, базовая линия «ключевые слова + стаж» их не видит.

## 8. Валидация (`D-4`)

Крейт `validate` прогоняет симуляции на **том же коде**, что и прод (`make validate`), и пишет `docs/validation/assessment.md`, `matching.md`, `paraphrase.md` + JSON рядом; `validate models` — сравнение моделей эмбеддингов (`embeddings.md`). Модель грузится в процесс из `models/` (`make model`) тем же кодом, что в сервисе; без неё близость описаний считается по ключевым словам, и отчёт это говорит. Результаты и их разбор — `docs/solution.md` §6.

### 8.1. Тестирование

- Синтетическая популяция: 400 кандидатов на специализацию с истинной θ ~ N(0, 1) → истинный грейд; процедура как в API и по той же `GradePolicy` (заявленный грейд → при провале сразу грейд ниже, вплоть до Junior).
- Сценарии: честная заявка; 20 % завышают и 10 % занижают грейд; *истинные* параметры заданий отличаются от калибровки, которой пользуется тест (a × 0,8…1,2, b ± 0,3), — устойчивость к неточной калибровке.
- Метрики:
  - точность классификации грейда и матрица ошибок;
  - **стабильность при пересдаче**: две независимые сессии (разные `seed`) → доля совпадений грейда, κ Коэна;
  - RMSE и смещение θ̂, средняя длина теста;
  - **дискриминативность**: `a` и точечно-бисериальная корреляция по шаблонам, список слабых шаблонов;
  - **устойчивость к утечке**: слабые кандидаты сдают тест на Middle; фиксированная форма из 15 заданий с утёкшими X % ответов против CAT + шаблонов, где «утечка» — все экземпляры 600 предыдущих сессий; сравнивается доля прошедших;
  - экспозиция: медианная и максимальная доля сессий, где показан шаблон;
  - доля пойманных person-fit «утечников».

### 8.2. Подбор

- Синтетические потребности и кандидаты со скрытой «истинной релевантностью» (функция от истинной θ, истинных навыков — включая незаявленные, — зарплаты и формата), отличной от функции скоринга.
- Тексты синтетические (`validate::texts`): в «о себе» — заявленный стек с тем же приукрашиванием, в описаниях мест работы — задачи по реальным навыкам (каждый с вероятностью 0,75) словами, отличными от вакансии; описание потребности пересказывает её навыки; отрасли сторон независимы. Тексты идут из отдельного потока случайных чисел, поэтому кандидаты и потребности — те же, что до появления текстов.
- 2 400 кандидатов, 120 потребностей для подбора весов и 120 отложенных для оценки; варианты весов сравниваются по nDCG@10 на обучающих, калибровка близости по смыслу — тоже по обучающим.
- Метрики: precision@10, nDCG@10, MAP, MRR. Базовые линии: случайный порядок, совпадение ключевых слов резюме + заявленный стаж, только косинус эмбеддингов. Абляции: без теста, без ФСП, без графа навыков, только навыки; источник близости описаний (по смыслу / по ключевым словам / не применяется) — на тех же весах, отдельно на профилях без заявленных навыков; корреляция близости с реальным покрытием обязательных навыков.
- **Пересказы вакансий** (`validate::paraphrase`): 12 демо-вакансий и их пересказы против разных вакансий той же и других специализаций и пяти похожих «не копий»; косинус, MinHash, ROC AUC и порог без ложных срабатываний.
- Экспертная разметка (10–20 реальных вакансий × топ-20, два эксперта) — следующий шаг; считать её будет прогон внешнего набора пар (ниже).
- **Внешний набор пар** (`matching::pairs`, CLI `validate pairs`, `POST /api/v1/eval/pairs`): вакансии, резюме и разметка 0–3 со стороны проходят через те же парсеры, скоринг и базовую линию «ключевые слова + стаж»; метрики — Precision@5/@k, nDCG@k, MAP, MRR. Недостающее не выдумывается: категория из резюме помечается «не подтверждена тестом», без теста — нейтральная сила результата 0,5 (середина грейда) с пометкой в объяснении, соседний грейд по умолчанию допускается. Близость описаний — по смыслу, если модель доступна (CLI — в процессе, API — через сервис, до 300 текстов в запросе), иначе пересечение основ слов, нормированное на лучшего, как `ts_rank` в API; режим и причина — в поле `text` отчёта. CLI кладёт рядом с отчётом векторы, с которыми он посчитан (`*.vectors.json`, коды `i8`), — по ним модульный тест воспроизводит закоммиченный отчёт без модели. Лимиты: 200 вакансий, 5 000 кандидатов, тексты до 20 000 символов; HTTP — тело до 8 МиБ и 10 запросов за 10 минут с IP.

## 9. Безопасность и 152-ФЗ (`N-7`)

### 9.1. Аутентификация и сессии
- Пароли: argon2id (m = 19 МиБ, t = 2, p = 1), строка в формате PHC.
- Подтверждение email: одноразовый токен 32 байта, в БД — только SHA-256 от него, срок 24 часа.
- Access JWT (EdDSA, 15 мин) + refresh (30 дней) — в httpOnly cookie: `fsp_at` (`SameSite=Lax`), `fsp_rt` (`SameSite=Strict`, путь `/api/v1/auth`), плюс маркер `fsp_session` без данных для редиректа на вход в Next; `Secure` в проде. Токен страница не видит, поэтому рядом лежит `fsp_at_exp` без `HttpOnly` — только время истечения access-токена (unix-секунды): клиент, увидев, что срок вышел (с запасом 10 с), сначала обновляет сессию и только потом шлёт запрос, а не ловит 401 и повторяет. Если устройство спешит и только что выданный токен по его часам уже «истёк», подсказка до перезагрузки страницы не используется — остаётся прежний путь через 401. Утечь здесь нечему: время истечения не даёт доступа. Refresh ротируется на каждом использовании; повторное использование старого → отзыв всего семейства. API-клиенты могут слать `Authorization: Bearer`.
- Изменяющие запросы с cookie (и без `Authorization`) требуют совпадения `Origin` (или `Referer`) с `PUBLIC_URL`, иначе 403 `csrf`.
- Rate limit: вход — 10 попыток за 15 минут на пару IP + email, регистрация — 20 в час с IP, повтор письма подтверждения — 3 в час на адрес, жалобы — 20 в сутки; отправка приглашений — квота компании (§11.1). Окна фиксированные; 429 несёт `Retry-After` — сколько секунд осталось до сброса окна того лимита, что отказал: TTL ключа в Valkey (`INCR` + `EXPIRE … NX` + `TTL` одной атомарной транзакцией), в памяти — до границы окна, у жалоб — пока самая старая из них не выйдет из суток.

### 9.2. Персональные данные
- **Шифрование полей**: email аккаунта, ФИО, телефон, Telegram, контактный email — XChaCha20-Poly1305, ключ из env, формат `v1 ∥ nonce (24 байта) ∥ ciphertext+tag`. Префикс — версия схемы: новая схема или ключ добавляются новой версией (§9.4); ротации ключа пока нет, ключ один.
- **Blind index** для поиска по email: HMAC-SHA256(ключ, нормализованный email).
- **Согласия**: версионированные документы; запись выдачи (время, IP, User-Agent) и отзыва. `required_for` — что обязательно при регистрации, `applies_to` — какие роли вообще могут выдать документ (видеозапись необязательна, но только для кандидата). Действующей у пользователя может быть только одна выдача каждой редакции документа (частичный уникальный индекс по `document_id`, то есть по версии), поэтому `POST /me/consents` идемпотентен; принимается только последняя редакция. Выдача старой редакции остаётся действующей: новая формулировка никого не снимает с публикации.
- **Публикация — только с согласием.** `PUT /candidate/privacy` с `visible: true` требует действующих `pd_processing` и `pd_publication` (любой редакции), иначе 409 `consent_required` с `document_id` текущей редакции первого недостающего. Отзыв любого из них ставит `visible = false`.
- **Пул поиска проверяет согласие сам** (защита в глубину): `db::pool::searchable_pool` — единственный источник `CandidatePool` для подборки, поиска по банку и статистики категорий — отбирает только кандидатов с неотозванной выдачей `pd_publication`; так же считаются `category_overview`, «коллеги» в статистике спроса, `candidate_invitable.published` (анонимный профиль, приглашение) и рынок категории для проверки вилки (§11.1). Правило записано один раз — представление `published_candidates` (миграция 0011): видим, есть `pd_publication`, до 18 лет — ещё и `guardian_consent` (§9.5). Представление — простой фильтр, планировщик встраивает его в запрос, и проверки остаются полусоединениями по частичному индексу `user_consents_document_idx`. Пул кешируется по специализациям (§12.2): отзыв согласия, скрытие профиля и любая другая запись, меняющая выдачу, сбрасывают кеш до ответа. Показанные карточки ещё раз сверяются с живыми таблицами (`searchable_among`): сохранённая подборка — при каждом показе (скрытый кандидат пропадает сразу, кроме компаний, с которыми у него уже есть приглашение или отклик), страница поиска по банку — тоже, поэтому скрытый профиль не покажет даже реплика, до которой поколение кеша ещё не дошло.
- **HTTP-кеш**: всё, что за cookie, токеном или API-ключом, и всё с ПДн отдаётся с `Cache-Control: private, no-store` — ни браузер на диск, ни прокси, ни CDN такой ответ не сохранят (§12.1).
- **Право на доступ (ст. 14)**: `GET /me/export` — JSON-вложение со всем, что хранится об аккаунте; задания, ответы и видео не выгружаются, сводка прокторинга — да. Работодатель получает аккаунт и данные компании. Обоим — уведомления, настройки писем и список отправленных писем (§13).
- **Политика обработки ПДн (ст. 18.1)**: публичная страница `/privacy` (серверный рендеринг), внизу — действующие тексты согласий с якорями `#pd_processing`, `#pd_publication`, `#terms`, `#proctoring_video`, `#guardian_consent`; на них ссылаются регистрация, шаг видеозаписи и страница представителя. Раздел `#minors` — правила для соискателей 14–17 лет.
- **Уведомления** (§13): в полезной нагрузке — только то, что получатель и так видит в кабинете; в письмах компании нет ФИО и контактов кандидата (по построению: в её полезной нагрузке нет таких полей), комментарий кандидата к отказу письмо не цитирует. Уведомления о кандидате или компании удаляются вместе с этим аккаунтом.
- **Удаление аккаунта**: профиль кандидата или компания удаляются со всеми данными, уведомления, письма и их настройки — тоже, строка `users` остаётся обезличенной (хэш вместо email) — журналы ссылаются на реальный id; у несовершеннолетнего — сразу и данные представителя (§9.5), видеозаписи — каталогом.
- **Журнал доступа к контактам**: кто, когда, на каком основании (приглашение или отклик), IP, канал (`cabinet` — кабинет, `api` — ATS компании по ключу, `webhook` — событие в ATS после принятия). Кандидат видит свою часть (`GET /candidate/contact-access`): компания, время, основание, канал — без сотрудника, IP и браузера.
- **Журнал модерации** (`moderation_actions`, миграция 0013): кто, когда, действие, объект, комментарий и детали (срок заморозки, закрытые жалобы, категория после аннулирования, название объекта на момент действия). Без внешних ключей — переживает аккаунты, как журнал доступа к контактам; строки не удаляются и не правятся. Каждое решение и действие пишется в одной транзакции с ним. **Каждый просмотр видеозаписи модератором** — строка `view_recording`, записанная до первого байта видео (проверка `HEAD` видео не отдаёт и просмотром не считается). Где кандидату это видно: у самого теста в истории — «Запись теста просмотрена модератором: дата», и в выгрузке ст. 14 (`recording_views`). Не в «Кто открывал ваши контакты»: запись — не контакты, а смешивать журналы значило бы путать кандидата. Кабинет модератора показывает журнал с фильтрами (действие, тип объекта, id объекта, кандидата или компании либо анонимный код кандидата «K-XXXXXX» — его модератор видит в очереди и карточке теста, а id нет) и курсором.
- **Видеозапись теста** (§5.6) — только с отдельного согласия `proctoring_video` (время, IP, User-Agent выдачи, как у остальных согласий). Без звука и без экрана; не используется для распознавания лица и установления личности.
  - **Хранение:** фрагменты — файлы `PROCTORING_DIR/<кандидат>/<сессия>/<seq>.bin` (в compose — именованный том `proctoring-data`), в Postgres только метаданные: выбор камеры, ссылка на выдачу согласия, номера и размеры фрагментов, события. Пути строятся из id из базы, не из ввода клиента.
  - **Шифрование:** каждый фрагмент — XChaCha20-Poly1305 тем же модулем, что поля ПДн (`v1 ∥ nonce ∥ ciphertext`), с привязкой к контексту `"proctoring" ∥ id сессии ∥ seq` как AAD: файл, перенесённый в чужую сессию или на другую позицию, не расшифруется. Отдаётся потоком, по одному фрагменту в памяти.
  - **Лимиты:** фрагмент до 1 МиБ, запись до 64 МиБ и 720 фрагментов (2 часа), до 50 событий за запрос и 500 на сессию.
  - **Срок хранения** 90 дней (`PROCTORING_RETENTION_DAYS`): фоновая задача удаляет файлы при старте и каждые 6 часов, затем помечает запись удалённой; сводка и события остаются. Тот же проход удаляет «осиротевшие» каталоги удалённых аккаунтов.
  - **Отзыв согласия** удаляет все записи кандидата сразу; **удаление аккаунта** — каскадом метаданные и каталог с файлами.
- **Хостинг** — VPS в РФ.

### 9.3. Разграничение доступа
- Роли: `candidate`, `employer`, `admin` (в интерфейсе — «Модератор», кабинет `/admin`). Роль проверяют extractor'ы `CandidateUser` / `EmployerUser` / `AdminUser` в аргументах хендлера (чужая роль — 403 `wrong_role`, без сессии — 401); black-box тест (`tests/blackbox/specs/moderation.spec.ts`) обходит все операции `/admin` из опубликованного OpenAPI с сессиями кандидата и работодателя и без сессии. Модератор создаётся только в базе: регистрация роль `admin` не принимает (422), в демо — `moderator@demo.fsp`.
- Кандидат видит только свои приглашения, отклики, тесты (`C-8`); каждый запрос фильтрует по `user_id` из токена.
- **Видимость контактов в типах**: DTO работодателя `CandidateCard` не содержит контактов. `CandidateContacts` создаётся только из `ContactGrant`, который возвращает единственная функция, проверяющая принятое приглашение или отклик и пишущая журнал.
- **ATS — тем же принципом** (§11.2): событие до принятия приглашения содержит `AtsCandidate::anonymous` (код и категория); имя и контакты попадают в него только через `AtsCandidate::disclosed`, который принимает `CandidateContacts`, а тот строится только из `ContactGrant`. Дерево `/api/v1/integrations` принимает только API-ключ (`ApiClient`), cookie и JWT туда не доходят.
- **Видео — тем же принципом**: в `CandidateCard` есть только `ProctoringBadge` (статус и число замечаний), без id сессии и ссылок. Запись отдают два эндпоинта: кандидату — его собственная (`CandidateUser` + фильтр по `user_id`), модератору — любая (`AdminUser`), и каждый его просмотр — строка журнала аудита. Для работодателя оба — 403, ни до «Принять», ни после. Карточка теста у модератора — без ФИО, контактов и email кандидата (§5.7).

### 9.4. Крипто-гибкость и ГОСТ
Алгоритм хранится вместе с данными (PHC-строка хэша, префикс версии шифротекста), шифрование и хэширование — за трейтами. Переход на ГОСТ (PBKDF2-HMAC-Стрибог по Р 50.1.111-2016, Кузнечик) и сертифицированное СКЗИ — добавление реализации и миграция по мере входа пользователей, без изменения схемы. В рантайме MVP ГОСТ не используем: соответствие требованиям даёт сертификация СКЗИ, а не сам алгоритм.

### 9.5. Соискатели 14–17 лет (наше дополнение)

Правило: **18+ по декларации или 14–17 с согласием законного представителя**; младше 14 — регистрации нет.

1. **Регистрация.** `RegisterRequest.age`: `adult` — больше ничего не спрашиваем, декларация пишется в `user_consents.age_bracket` каждой выданной при регистрации записи; даты рождения у взрослых нет. `minor` — обязателен блок `minor`: дата рождения (сервер проверяет 14–17 на сегодня, `age::check_minor_birth_date`) и ФИО и email представителя (не совпадает с почтой аккаунта). «Мне меньше 14» — форма не отправляется, на сервере такого варианта нет. Работодатель — взрослый по декларации в блоке согласий («Я представляю компанию и мне есть 18 лет»), его выдачи тоже помечаются `adult`.
2. **Хранение.** `candidates.birth_date` — только у 14–17. `guardian_requests` — по строке на представителя: ФИО и email зашифрованы как прочие ПДн, у email — blind index (лимит писем на адрес и проверка «не своя почта»), SHA-256 двух ссылок последнего письма, срок ссылки ответа, решение (`granted` / `declined`), ссылка на выдачу. Само согласие — обычная запись `user_consents` подростка на документ `guardian_consent` (версионированный, `applies_to = {candidate}`, `required_for` пуст) с IP и User-Agent представителя. `POST /me/consents` этот документ не выдаёт, отзыв из кабинета его не трогает (404).
3. **Письмо** уходит после подтверждения email подростка (`verify-email`): аккаунт, почту которого никто не подтвердил, не может заставить платформу писать третьему лицу. Две ссылки одного письма на `/guardian/confirm?token=…`: **ответ** — одноразовый, 7 дней, «Подтверждаю» или «Не согласен»; **отзыв** — пока согласие действует (до ответа работает как отказ). Повтор письма и смена адреса перезаписывают хэши — старые ссылки гаснут. Лимит: 3 письма в час на подростка, 5 в сутки на адрес (Valkey). Повтор после отказа или отзыва — новая строка, прежний ответ остаётся в истории.
4. **«Несовершеннолетний» вычисляется в момент запроса**: `birth_date + interval '18 years' > current_date`; в Rust — `age::adult_from` (обе стороны переносят 29 февраля на 28-е). Ни расписаний, ни флагов: в день 18-летия ограничения снимаются сами. Исключение — кеш пула поиска (§12.2): он вычисляет признак при загрузке снимка, поэтому выдача поиска учитывает 18-летие с задержкой до 30 с после полуночи.
5. **Публикация.** `PUT /candidate/privacy` с `visible: true` у несовершеннолетнего без действующей выдачи `guardian_consent` → 409 `guardian_consent_required`. Пул поиска, флаги `published`/`searchable` в `db::pool::candidate_cards`, статистика категорий, «коллеги» в статистике спроса, `candidate_invitable.published` и рыночная вилка (§11.1) читают представление `published_candidates`, где есть условие «взрослый или есть действующее согласие представителя» — тем же полусоединением по `user_consents_document_idx`. Отказ и отзыв ставят `visible = false`. До согласия кабинет и тест доступны, а оба пути, которые открывают компании контакты, — отклик на вакансию и принятие приглашения — отвечают тем же 409.
6. **Работодатель.** `CandidateCard.minor` — нейтральная отметка «14–17 лет», дата рождения в DTO не попадает. В окне приглашения — памятка о ТК РФ (ст. 63, 92, 94, 265). Фильтр `adults_only` («Только 18+») в поиске по банку и в фильтрах подборки отсекает несовершеннолетних по признаку `minor` из SQL пула — это фильтр, а не штраф в скоринге.
7. **Срок хранения** (`age::GUARDIAN_RETENTION_DAYS = 30`): через 30 дней после 18-летия стираются ФИО, email, blind index и хэши ссылок представителя (`erased_at`), его IP и User-Agent в выдаче и сама дата рождения — аккаунт становится обычным взрослым. Остаётся факт: редакция документа, время выдачи и отзыва. Задача `guardian::sweep` — при старте и каждые 6 часов. 30 дней — запас на разбор спора о том, что происходило, пока согласие было основанием обработки. При удалении аккаунта: строки `guardian_requests` уходят каскадом с профилем, IP и User-Agent выдачи обнуляются.
8. **Выгрузка (ст. 14)**: `candidate.age` — возрастная группа на сегодня, дата рождения, все запросы к представителям с ответами; у каждой записи согласия — объявленный возраст `age_bracket`.
9. **Демо-данные**: первый кандидат-junior с категорией в каждой специализации — 14–17 лет (отдельный поток RNG `MINORS_SEED`, остальное демо не меняется); у четырёх согласие подтверждено, двое ждут ответа, один из них — вход `minor@demo.fsp`.

## 11. Антифейк и концепции вне MVP (`X-1`, `X-2`)

### 11.1. Антифейк (`X-1`) — реализовано

Ни один сигнал не блокирует публикацию и приглашение: он предупреждает работодателя, снижает уровень доверия (и квоту) и попадает в очередь модерации `GET /admin/antifake` (ниже). Блокирует только решение модератора. Правила — чистый модуль `matching::trust`, сервис — `api::trust`, данные — миграция `0008_trust_signals`.

| Сигнал | Правило |
|---|---|
| Домен | Подтверждённая почта входа и сайт на одном домене, поддомены в обе стороны. Публичная почта (gmail.com, yandex.ru, mail.ru, bk.ru, inbox.ru, list.ru, rambler.ru, outlook.com, icloud.com, proton.me, …) и её поддомены — никогда; общие зоны (`com.ru`, `github.io`, …) и TLD не база. Сравнение в ASCII (punycode, свой кодер RFC 3492). Пересчёт при сохранении профиля и открытии раздела «Доверие и квота»; кандидат видит `company_verified_domain` → «Домен подтверждён» |
| Вилка выше рынка | `max > 1.5 × p90` ожиданий кандидатов категории — тех же, что в карточках категорий (`published_candidates`: видимые, с согласием на публикацию, 14–17 лет — с согласием представителя, поиск не закрыт), при ≥ 5 ожиданиях |
| Широкая вилка | `max ≥ 3 × min` |
| Пересказ чужой вакансии | Косинус эмбеддингов (§6.4) с опубликованной за 90 дней вакансией другой компании ≥ 0,953 → `paraphrase_of_other`; проверяет воркер эмбеддингов через несколько секунд после публикации. Квоту не снижает — сходство по смыслу ошибается чаще дословного: только очередь модерации и примечание в карточке вакансии работодателя (без имени оригинала) |
| Дубли | Подпись: пары соседних слов → MinHash 128 × u32; сходство = доля равных слотов, порог 0,6. Своя вакансия → `duplicate_own` и подсказка «обновите существующую»; чужая опубликованная за 90 дней → `copy_of_other` (сравнение с 2 000 последних опубликованных); свои — черновики и опубликованные. Тексты короче 12 пар слов подписи не получают. Подпись пишется при каждом сохранении, старые строки подписываются при старте API |
| Поведение | Жалобы кандидатов (уникальные, не отклонённые модератором, 90 дней), отказы «зарплата»/«компания», отзывы, приглашения без ответа, принятые приглашения (180 дней) |

**Квота:** `10 + min(бонусы, 20) + штрафы`, в пределах 5…30. Бонусы: домен +10, 30 дней на платформе +10, 3 принятых приглашения +10 (+5 после первого). Штрафы: жалоба −10 (до −30); ≥ 40 % «плохих» отказов при ≥ 5 отказах −10; вилка-отметка −5 (до −10); копия чужой вакансии −20; ≥ 30 % отзывов при ≥ 5 приглашениях −5; ≤ 10 % ответов при ≥ 10 закрытых −5; дубли своих −5. Уровни: `low` (есть штрафы и квота ≤ 10), `high` (30), `new` (< 30 дней без штрафов), иначе `standard`. Кандидату о вилке не показываем ничего — обоснование в docs/solution.md §10.1.

**Заморозка модератором** — не сигнал, а решение: квота 0 до конца срока, ниже пола 5, уровень `frozen`, причина «Модератор приостановил приглашения до …» с вкладом −квота; отправка приглашения — 409 `invitations_frozen` с датой.

**Модерация** (`moderation`, кабинет «Антифейк и жалобы»). Одна очередь `GET /admin/antifake` сводит четыре вида: жалобы (открытые), вакансии и приглашения с непросмотренными отметками и компании с отрицательными сигналами, которые модератор ещё не смотрел или у которых после этого появилась новая жалоба, отметка или отказ «зарплата/компания». Порядок — по времени попадания в очередь, курсор `(time, id)`: каждый источник отдаёт следующую страницу после курсора, страницы сливаются; компании считаются в памяти тем же `matching::trust::assess`. Кабинет показывает загруженное по компаниям: у раздела — название, уровень доверия, квота и пауза приглашений, внутри — жалобы, отметки вакансий и приглашений и сама компания; первым идёт раздел, чей сигнал ждёт дольше всех, а следующая страница может добавить элементы в раздел выше. Вид «Действующие меры» — снятые вакансии и замороженные компании, их можно вернуть. Действия, у каждого обязательный комментарий:

| Действие | Применимо к | Эффект |
|---|---|---|
| Снять (`dismiss`) | отметке вакансии или приглашения, жалобе, компании | отметка `dismissed` — перестаёт снижать квоту; жалоба закрыта как необоснованная — перестаёт снижать квоту; компания уходит из очереди до следующего сигнала, квота не меняется |
| Снять с публикации | опубликованной вакансии или жалобе на неё | вакансия закрыта, `unpublished_at`, публикация через API — 409 `vacancy_unpublished`; её отметки `upheld` (продолжают считаться), открытые жалобы на неё закрыты как подтверждённые |
| Приостановить приглашения на N дней (1–90) | компании или любому её элементу | квота 0 до конца срока; жалобы на компанию и её приглашения (и жалоба, из которой действие) закрыты как подтверждённые; отметка элемента — `upheld` |
| Вернуть | снятой вакансии, замороженной компании | вакансия снова опубликована, её отметки — `dismissed`; заморозка снимается досрочно |

Открытая жалоба — одна на человека и объект: повторная отправка (двойной клик, вторая вкладка) возвращает ту же жалобу и не считается ещё раз; после решения модератора можно пожаловаться снова. Подтверждённая жалоба продолжает снижать квоту свои 90 дней, отклонённая — сразу перестаёт. Компания видит решения о себе, своих вакансиях, приглашениях и жалобах на них в разделе «Доверие и квота» (`TrustStatus.moderation`: что произошло и комментарий модератора; автор жалобы не называется) и баннер о заморозке; снятая вакансия помечена в кабинете.

**Дальше:** проверка ИНН/ОГРН по ЕГРЮЛ; подтверждение домена DNS TXT; отчётность модерации (время реакции, доля подтверждённых жалоб); порог пересказа — по разметке модераторов, а не по 12 пересказам.

### 11.2. Интеграция с ATS работодателя (`X-2`, реализовано)

Нативные коннекторы — концепция в `docs/solution.md` §10.2.

```
изменение статуса ─┐ одна транзакция
                   ├─▶ invitations / applications  +  integration_events (outbox, тело зашифровано)
                   │                                          │ claim_due_events: FOR UPDATE SKIP LOCKED + аренда 60 с
                   │                                          ▼
                   │                                 диспетчер (tokio, в каждой реплике api)
                   │                                          │ POST, FSP-Signature, без редиректов, DNS только в публичные адреса
                   │                                          ▼
                   │                                   ATS компании ──▶ POST /api/v1/integrations/outcomes (API-ключ)
                   │                                                ──▶ GET  /integrations/invitations | candidates/{id}
                   │                                                ──▶ POST /integrations/needs
```

- **Outbox.** Событие пишется в той же транзакции, что и смена статуса: `invitation.sent|viewed|accepted|declined|expired|withdrawn`, `application.created|status_changed`, `contacts.opened`. Не записалось событие — откатывается и смена статуса, и запись в журнале доступа. Истечение приглашений ленивое, как и раньше, — `UPDATE … RETURNING` в транзакции с событиями. Компания без вебхука событий не получает — значит, и раскрытия нет.
- **152-ФЗ в типах.** До принятия — анонимный код и категория; после принятия или отклика — ФИО, контакты, ссылки на профиль и PDF, только через `ContactGrant` (канал `webhook` в журнале доступа). Тело события зашифровано тем же XChaCha20-Poly1305 с привязкой к id события; завершённые события удаляются через 30 дней; удаление аккаунта кандидата удаляет его события.
- **Доставка.** Диспетчер в каждой реплике забирает до 16 событий с `FOR UPDATE SKIP LOCKED` и сразу сдвигает `next_attempt_at` на 60 с (аренда): реплики не берут одно событие, а упавшая реплика его не теряет. Ответ 2xx — `delivered`; иначе повтор через 1 мин, 5 мин, 30 мин, 2 ч, 12 ч, пока следующий повтор укладывается в сутки от создания, затем `failed` (у адреса, который не отвечает, — после шестой попытки, ≈ 14,6 ч). Каждая попытка — строка журнала (код, задержка, ошибка). «Отправить ещё раз» — снова в очередь с новым суточным окном. Гарантия «хотя бы один раз», получатель дедуплицирует по `FSP-Event-Id`.
- **Подпись.** `FSP-Signature: t=<unix>,v1=hex(HMAC-SHA256(secret, t + "." + тело))`; метка внутри MAC, получатель отклоняет `t` старше 5 минут — перехваченный запрос не повторить. Секрет `whsec_…` показывается один раз, хранится зашифрованным (контекст — id компании); после смены сутки идут две подписи.
- **SSRF.** Только `https://`, без логина в URL и редиректов. Проверка адреса — внутри DNS-резолвера клиента, на каждом соединении: непубличные адреса (loopback, частные сети, link-local с 169.254.169.254, CGNAT, multicast, зарезервированные, IPv6-аналоги и IPv4 внутри IPv6) отбрасываются, соединение идёт только на публичные, а имя без публичных адресов отклоняется — DNS rebinding во внутреннюю сеть не проходит. Исключение — хосты из `WEBHOOK_DEV_HOSTS` (демо-ATS в compose): им можно `http` и внутренний адрес.
- **API-ключи.** `fsp_live_` + 256 случайных бит; хранится SHA-256 и видимый префикс, ключ показывается один раз. Скоупы `invitations:read`, `candidates:read`, `outcomes:write`, `needs:write` — битовая маска в горячем пути. Лимит 120 запросов в минуту на ключ (Valkey / in-memory `Kv`), «последний запрос» пишется не чаще раза в минуту, не больше 10 действующих ключей.
- **Этапы найма.** `POST /integrations/outcomes` — только по принятому приглашению или неотозванному отклику; повтор этапа обновляет его. Кандидат видит «Компания отметила: собеседование» в приглашении или отклике, работодатель — этапы в воронке. Это реальные метки найма для будущей калибровки весов подбора (§6.3).
- **Опрос вместо вебхука.** `GET /integrations/invitations` отдаёт изменения по возрастанию «времени изменения» приглашения (создано, открыто, отвечено, отозвано, истекло) с курсором `(время, id)`. Время ставит `now()` транзакции — момент её начала, а видно изменение становится в момент коммита. Курсор по одному времени терял бы изменения: транзакция A началась раньше, B позже, B закоммитилась, опрос забрал B и сдвинул курсор, A закоммитилась со временем меньше курсора — и навсегда пропала. Поэтому страница останавливается на горизонте: не позже «сейчас − `ATS_POLL_LAG_SECS`» (5 с) и не позже начала самой старой транзакции этой базы, которая уже что-то пишет (`pg_stat_activity`, `backend_xid`). Всё, что новее горизонта, придёт следующим опросом; задержка покрывает и транзакции, которые ещё не начали писать. Ленивое истечение выполняется в начале опроса и ждёт блокировки строк, которые истекает параллельная транзакция. Горизонт — SQL над `pg_stat_activity`, снаружи его не проверить (§14); чистая часть — курсор и его возврат на пустой странице — покрыта модульными тестами `routes::ats`. Пустая страница возвращает тот же курсор, прежний параметр `since` — курсор «после этого момента».
- **Импорт вакансий.** `POST /integrations/needs` разбирает текст тем же `matching::parse_need`, что и форма потребности; без специализации или вилки — 422. С `external_id` (id вакансии в ATS) импорт идемпотентен: `INSERT … ON CONFLICT DO NOTHING` по частичному уникальному индексу `(company_id, external_id)`, повтор и одновременная отправка получают 200 и потребность, созданную первой.

**Масштабирование:** stateless api за балансировщиком; Valkey для общих лимитов и поколения кешей (§12.2); read-реплика Postgres; аналитика событий — CDC в ClickHouse; эмбеддинги — отдельный воркер.

### 12.1. HTTP-кеширование

По умолчанию ответ API — `Cache-Control: private, no-store`: внешний слой `http_cache::private_by_default` ставит его всему, что не помечено явно. Это всё за cookie, Bearer-токеном или API-ключом и всё с ПДн: по 152-ФЗ такой ответ не должен оседать ни в общем кеше, ни у посредника, ни на диске браузера. Публичное кеширование включает группа роутов (`from_fn_with_state(Policy, http_cache::public)`), а не хендлер; тест в `lib.rs` сверяет по OpenAPI, что в публичных группах нет методов с `security`.

| Маршрут | Cache-Control | Валидатор |
|---|---|---|
| `GET /catalog`, `/catalog/skills`, `/consents/current` | `public, max-age=300, stale-while-revalidate=86400` | ETag, `If-None-Match` → 304; тело и ETag `/catalog` считаются один раз на процесс |
| `GET /vacancies`, `/vacancies/{id}`, `/vacancies/{id}/similar` | `public, max-age=30, stale-while-revalidate=120` | ETag → 304. В ответе — вакансии и компании, ПДн нет |
| `/guardian/consent` (GET, POST), `POST /eval/pairs`, `GET /catalog/test-plan` (каждый раз новые примеры) | `no-store` | — |
| всё остальное, включая ошибки и `/integrations/*` | `private, no-store` | — |
| 401 | `private, no-cache` | — |

Публичная политика действует только для 200 на GET/HEAD без `Set-Cookie`; ошибки получают `no-store`. У 401 нет данных, и он получает `private, no-cache`: Chrome не завершает ответ с `no-store`, пока страница не прочитает тело, а проверка сессии в шапке публичных страниц тело 401 не читает — каждый такой ответ держал бы соединение HTTP/1.1 до сборки мусора (и `networkidle` в e2e не наступал). Ответы с данными, включая `/auth/refresh` и `/auth/login` с токенами (RFC 6749 §5.1), остаются `no-store` — клиент обязан прочитать или отменить их тело (`res.body?.cancel()`). ETag — 64-битный SipHash тела с фиксированными ключами, одинаковый у всех реплик. `If-None-Match` сравнивается слабо (RFC 9110): Caddy при сжатии дописывает к ETag `-zstd` и снимает суффикс со входящего заголовка — 304 проходит.

Caddy (`deploy/Caddyfile`):
- `/_next/static/*` — `immutable` на год (ставит Next: в путях хэш содержимого);
- файлы `web/public` (`/brand/*`, `/icon.svg`) — `public, max-age=86400, stale-while-revalidate=604800`: имена между сборками не меняются, поэтому не immutable;
- предрендеренные страницы Next отдаёт с `s-maxage=31536000` — CDN держал бы год HTML со ссылками на чанки прошлой сборки. Caddy заменяет его на `public, max-age=0, must-revalidate, s-maxage=60, stale-while-revalidate=300`: браузер на каждом заходе сверяет ETag (дешёвый 304), общий кеш держит страницу минуту. Динамические страницы сохраняют `private, no-store` от Next;
- сжатие: страницы и статика — `zstd better` и `gzip 6`, ответы `/api/*` — `zstd` уровня по умолчанию и `gzip 6`. JSON API личный и сжимается заново на каждый ответ: `better` тратил на него вдвое больше процессора Caddy ради 1–11 % байтов (docs/solution.md §12.4). Next сам не сжимает (`compress: false`);
- память Caddy — 256 МБ и `GOMEMLIMIT=200MiB`: 50 одновременно сжимаемых страниц занимают до ~150 МБ, при прежних 64 МБ контейнер убивало OOM по кругу.

### 12.2. Кеш пула кандидатов и карточек

Подборка, поиск по банку, рекомендованные категории потребности и объяснение в профиле ранжируют пул специализации. Раньше он собирался из SQL на каждый запрос; при 10 000 кандидатах это 25–60 мс работы Postgres на запрос, и поиск под 50 одновременными клиентами держал 84 запроса в секунду. Потом главным расходом стали карточки показанных кандидатов — их теперь тоже держит снимок.

- **Снимок специализации** (`pool::SpecPool`): компактный `CandidatePool` (горячие записи, интернированные навыки), id по возрастанию, битсет «до 18», векторы профилей в `i8` (§6.4), до 8 наборов близости по смыслу для разных векторов потребностей и до 8 наборов `ts_rank_cd` для разных текстов потребностей (прямое отображение по SipHash текста: ранжирование длинного OR-запроса стоит столько же, сколько загрузка снимка). Снимок лежит в `ArcSwapOption`, по слоту на специализацию. Запрос копирует только прошедшие фильтры горячие записи (`CandidatePool::subset`), навыки и холодные данные общие. Фильтры (грейд, «Только 18+», ФСП, ожидания, навыки) применяются в памяти; близость текста нормируется на лучший результат среди кандидатов нужного грейда и возраста — как раньше в SQL. На тех же данных результат совпадает со старым путём: порядок, баллы до 0,001 и объяснения (86 сравнений подборок, поиска и профилей на 10 000 кандидатах).
- **Карточки** (`cards::CachedCard`). Снимок держит по слоту `ArcSwapOption` на кандидата — холодные данные отдельно от горячего `CandidatePool`. Слот заполняется при первом показе: карточки, которых в кеше нет, читаются полным запросом (`db::pool::candidate_cards`) и сразу кладутся в снимок своей специализации. Для закешированных выполняется лёгкий запрос живых полей (`db::pool::card_live`): опубликован ли профиль (тот же `published_candidates`), статус поиска, флаги приватности, последняя активность, «до 18», отношение компании (последнее приглашение, отклик). Всё остальное — навыки, ФСП, опыт, «о себе», задания, бейдж прокторинга, расшифрованное имя — берётся из памяти. Карточка годится, только пока живые флаги `show_name`, `show_fsp`, `show_experience` совпадают с теми, с которыми она собрана; иначе она читается заново. Карточки живут ровно столько, сколько их снимок, и пропадают вместе с ним — после записи, меняющей выдачу или карточку, и не позже чем через 30 с. Кандидаты вне снимка (закрыли поиск, но связаны с компанией откликом или приглашением) всегда читаются полным запросом. Память — около 3 КБ на показанного кандидата (10 000 кандидатов — до ~30 МБ). Профиль кандидата ищет карточку во всех текущих снимках, показ сохранённой подборки сначала загружает снимок специализации потребности.
- **Поколение.** Снимок помнит поколение, прочитанное до загрузки (`cache::Stamp`). Каждая запись, меняющая выдачу или карточку, после коммита вызывает `CandidateCache::invalidate`: локальная эпоха (атомик) и `INCR cache:candidates:generation` в Valkey. Другие реплики читают счётчик не чаще раза в 250 мс (`REMOTE_TTL`); без Valkey работает только локальная эпоха. Жёсткий TTL снимка — 30 с (`HARD_TTL`); снимок, у которого истёк только TTL (поколение то же), ещё до 5 с (`RELOAD_GRACE`) обслуживает запросы, пока один из них его перезагружает, — иначе раз в 30 с все запросы вставали бы в очередь за загрузкой. Снимок старого поколения не отдаётся никогда.
- **Сбрасывают кеш:** вектор профиля или потребности, записанный воркером эмбеддингов (или удалённый вектор профиля, когда его текст опустел); профиль и заявленные навыки, навыки из резюме, опрос, присвоение категории с навыками из теста, приватность и статус поиска, отказ от приглашения с причиной «не ищу работу» (закрывает поиск), выдача и отзыв согласий, решение законного представителя, привязка, синхронизация и отвязка ФСП (вместе с навыками из ФСП, §7.4), сверка навыков из ФСП при старте API, если она что-то изменила, удаление аккаунта. Ради карточек — ещё сдача решения задания и его оценка работодателем (счётчик и средняя оценка заданий) и загрузка фрагмента видео или событий целостности после завершения теста, в 60-секундное «окно хвоста» (бейдж прокторинга последнего присвоения грейда; во время теста сессия ещё не стала основанием грейда, и записи кеш не трогают). Это редкие записи: один-два сброса на тест или задание.
- **Ждут TTL (≤ 30 с):** время последней активности в ранжировании (тест, задание, отклик — признак актуальности в масштабе 60 дней; в карточке оно живое), 18-летие для фильтра «Только 18+» (признак «до 18» снимка считается при загрузке; в карточке — живой), очистка данных представителя (выдачу не меняет), записи в обход API, `INCR`, потерянный при недоступном Valkey, смена суток для затухания баллов ФСП в карточке. На другой реплике запись, сбросившая поколение, доходит до карточек не позже 250 мс.
- **152-ФЗ: видимость — сразу.** На той же реплике запись сбрасывает кеш до ответа, и следующий запрос строит пул заново. Каждая показанная карточка, из кеша или нет, сверяется с живыми таблицами: публикация, статус поиска и флаги приватности читаются на каждом показе (`card_live` или `candidate_cards`). Поэтому реплика, до которой поколение ещё не дошло, и даже запись в обход API не покажут ни скрытый профиль, ни профиль без согласия на публикацию, ни подростка без согласия представителя, ни имя, данные ФСП или названия компаний, которые кандидат только что скрыл; такой профиль разве что учтётся в `total` до 250 мс. Правила поколения, повторного использования карточки и фильтров пула — модульные тесты `cache`, `cards`, `pool`; отзыв согласия и возврат в поиск — black-box (`privacy.spec.ts`); межреплицевое распространение не проверяется (§14).
- **Одна загрузка на промах.** Слот грузит один запрос, остальные ждут его (`cache::Flight`: `AtomicBool` + `tokio::sync::Notify`, без мьютексов); упавшая или отменённая загрузка освобождает слот. Так же ранжирование текста потребности (`ts_rank_cd`, ~25 мс на 10 000 кандидатах) считается одним запросом на слот снимка: после перезагрузки снимка его раньше пересчитывал каждый ожидавший запрос.
- **Метрики.** `cache_lookups_total{cache, result}` — попадания и промахи пула (`pool`), карточек (`card`, по карточке), статистики категорий (`category_stats`) и компании работодателя (`company`); счётчики `metrics` разрешаются один раз при создании кеша, инкремент — один атомик. Панели — в дашборде Grafana «API».
- **Компания работодателя** — её id нужен каждому запросу кабинета работодателя. Компания создаётся вместе с аккаунтом, владелец у неё не меняется, удаляется она только с аккаунтом, а удаление аккаунта сбрасывает поколение. Поэтому id лежит в памяти процесса (1024 слота `ArcSwapOption`, прямое отображение по SipHash id владельца) и годится только для поколения, в котором прочитан, и не дольше `HARD_TTL`. Другие сессии удалённого аккаунта на той же реплике получают 409 `company_profile_required` сразу (модульный тест слота компании в `cache`), на другой — не позже 250 мс. Отсутствие компании не запоминается.
- **Статистика категорий** (`GET /employer/categories`) и спрос в категории кандидата (`GET /candidate/market`; счётчик «компании смотрели вас» личный и читается всегда) кешируются тем же механизмом. Спрос включает приглашения и потребности за 30 и 90 дней — для них достаточно жёсткого TTL. Храним в памяти процесса, а не в Valkey: десяток строк на реплику дешевле сетевого запроса на каждом обращении.

Индексы под горячие запросы — миграции `0009_perf_indexes` и `0012_candidate_side_indexes` (замеры — docs/solution.md §12.4).

### 12.3. Путь запроса

Профиль под нагрузкой (samply) и правки по нему — docs/solution.md §12.4.

- **Middleware.** `AppState` — один `Arc` на все сервисы: axum клонирует состояние несколько раз за запрос, и двенадцать счётчиков ссылок, общих для всех ядер, съедали 28 % процессора на `/healthz`. Слои, которым не нужен шаблон маршрута (catch-panic, `x-request-id`, скрытие `Authorization`/`Cookie` в трейсах, трейсинг, таймаут 30 с, лимиты тела, `Cache-Control` по умолчанию), обёрнуты вокруг роутера один раз — tower-стеком в `lib.rs::app`. Через `Router::layer` они оборачивали бы каждый маршрут, а axum клонирует стек маршрута на каждый запрос и ещё раз внутри каждого `from_fn`. Метрики (читают шаблон маршрута) и CSRF (его отказы попадают в метрики) остались на маршрутах. `x-request-id` — UUIDv4 из потокового генератора, без системного вызова на запрос.
- **JWT.** Проверка подписи Ed25519 (~50 мкс) была четвертью процессора на закешированных маршрутах. Токен, чей точный текст уже прошёл проверку, берётся из таблицы на 1024 слота (`ArcSwapOption`, сравнение текста без раннего выхода); срок действия проверяется каждый раз, отзыв — как раньше, в Valkey. Подделанный токен совпасть с проверенным не может: сравнивается весь текст, а не хэш.
- **Пул соединений.** sqlx по умолчанию пингует соединение перед каждой выдачей из пула — второй обмен с Postgres на каждый запрос. Пингуется только соединение, простоявшее не меньше секунды; если сервер пропал за эту секунду, запрос завершится ошибкой, и пул выбросит соединение. Размер пула — `DATABASE_POOL_SIZE`, по умолчанию 16 при `max_connections = 100` у Postgres (запас на пять реплик). Больше соединений, чем ядер у базы, только переносит очередь внутрь Postgres: на 10 ядрах и 50 клиентах 32 соединения дают ту же пропускную способность, что 16, но p95 поиска 120 мс вместо 25; 8 — на 9 % меньше запросов при p95 10 мс. Кеш подготовленных запросов sqlx — 100 на соединение при нескольких десятках горячих.
- **Карточки кандидатов** — из кеша снимка (§12.2) и один лёгкий запрос живых полей (`db::pool::card_live`); незакешированные — один полный запрос (`db::pool::candidate_cards`): навыки и задания агрегируются в подзапросах `LATERAL` по каждому кандидату, отношение компании (последнее приглашение, отклик), бейдж прокторинга последнего присвоения грейда и флаги видимости — в той же строке. Раньше это были четыре запроса, и основной группировал широкие строки кандидатов по навыкам. Массив id передаётся через подзапрос `(SELECT $2::uuid[])`: с видимым массивом из одного id Postgres планировал запрос заново на каждый вызов и не переходил на общий план: 0,5 мс на профиль вместо 0,12 мс. «Откликался в компанию» — скалярный подзапрос с `LIMIT 1` по `applications (candidate_id)`, а не `EXISTS`: `EXISTS` планировщик превращал в хешированный проход по всем откликам компании. Задания карточки читались полным проходом по `task_assignments` на каждого кандидата — индекса по кандидату не было (миграция 0012).
- **Сохранённая подборка.** Объяснение хранится как `json` (миграция 0010): пишется и читается целиком, а `jsonb` на каждом чтении переводился в текст, который API разбирал в `serde_json::Value`, затем в структуру и сериализовал обратно. Теперь текст вставляется в ответ как есть (`RawValue`). Пересборка пишет 30 строк одним `INSERT … SELECT FROM UNNEST` и считает всё до блокировки строки потребности; помечает устаревшими только строки текущей выдачи. Блокировка держится на три запроса и коммит вместо 32.
- **Логи и метрики** на запрос не стоят ничего заметного: построчного журнала запросов нет (span `TraceLayer` — уровня DEBUG, фильтр его отбрасывает), метрики — ~1,5 % процессора `/healthz`.

- **Атомарность.** Уведомление пишется в той же транзакции, что и изменение (как outbox ATS, §11.2): не записалось — откатывается и приглашение, и раскрытие контактов. Откат по сбою записи не проверяется тестами: для этого нужна инъекция отказа в базу (§14).
- **152-ФЗ в типах.** Полезная нагрузка — `notify::Event`, у каждого вида своя структура. У компании кандидат — это `candidate_code` и `candidate_id`, полей для ФИО и контактов нет, поэтому их нет и в письме; комментарий к отказу (свободный текст кандидата) письмо компании не цитирует. Тесты рендерят письмо о принятии по настоящему принятию и проверяют, что ФИО, телефона, почты и Telegram в нём нет.
- **Хранение.** Текст не хранится — собирается при чтении из полезной нагрузки (`json`, читается целиком), поэтому правка формулировки доходит и до старых уведомлений. Виды — `#[repr(u8)]` перечисление; настройки писем — битовая маска `i32`, бит = номер вида, номера не меняются. Новый вид: вариант в конце `NotificationKind`, полезная нагрузка, тексты в `render` и миграция, расширяющая `CHECK`.
- **Правило частоты** (`NotifyConfig`, переменные `NOTIFY_EMAIL_*`): уведомление ждёт 2 минуты (`hold`) — всё, что придёт за это время, уйдёт одним письмом; получателю — не чаще одного письма в 10 минут (`min_gap`) и не больше 10 за сутки (`daily_cap`). Если правило не пускает, ожидающие уведомления переносятся вместе и продолжают собираться в одно письмо — ничего не теряется.
- **Приглашение не ждёт паузы между письмами.** `invitation_received` — то, ради чего соискатель здесь, поэтому этот вид (`NotificationKind::skips_gap`) пропускает 10-минутную паузу: когда его 2 минуты сбора кончились, письмо уходит сразу и забирает всё, что накопилось у получателя к этому моменту. Суточный лимит действует и для него. При переносе по паузе ожидающие приглашения остаются на своём времени (переносится только остальное), при переносе по суточному лимиту — переносятся со всеми. Раньше письмо о приглашении, пришедшем через 2 минуты после другого письма, ждало конца паузы — до 8 минут — и приходило под темой «2 новых уведомления»; все три правила проверяет модульный тест чистой функции `notify::email::plan`.
- **Тема письма.** Одно событие — его заголовок. Если в письме есть приглашения, оно начинается с самого нового: тема — «Компания приглашает: роль (и ещё 1 уведомление)», при одних приглашениях — «… (и ещё 2 приглашения)», и в тексте это приглашение стоит первым, остальное — в порядке поступления. Без приглашений — «3 новых уведомления». Сборка одного получателя в нескольких репликах сериализована `pg_try_advisory_xact_lock`.
- **Доставка «хотя бы один раз».** Id письма — Message-ID: повтор после сбоя между SMTP и записью статуса — то же письмо для почтового клиента. Вид, отключённый после постановки в очередь, при отправке выпадает; если не осталось ничего — письмо `skipped`.
- **Отписка.** В каждом письме — `List-Unsubscribe: <…/api/v1/notifications/unsubscribe?token=…>` и `List-Unsubscribe-Post: List-Unsubscribe=One-Click` (RFC 8058), в тексте — ссылка на страницу `/notifications/unsubscribe` с кнопкой: GET ничего не отключает, отключает POST. Токен: версия, id аккаунта, вид (или «все»), HMAC-SHA256 обрезанный до 16 байт; ключ выводится из `BIDX_KEY` (`Crypto::derive_key`), срока нет. Письмо одного вида отписывает от этого вида, сводное — от всех писем.
- **Напоминание** раз в 5 минут (`notify::sweep`): неотвеченные приглашения, у которых до истечения меньше 48 ч; единственность держит уникальный `(user_id, dedup_key = 'expiring:<id>')` — два обхода в двух репликах пишут одно напоминание. Тот же обход сверяет уровень доверия и квоту каждой компании с `company_trust_seen` под блокировкой строки; первый взгляд только запоминает.
- **Кабинет.** Колокольчик со счётчиком в шапке обоих кабинетов, выпадающий список последних 8, «Отметить всё прочитанным», страница `/candidate|employer/notifications` с пагинацией по ключу. Счётчик опрашивается раз в 30 с одним наблюдателем на кабинет (TanStack Query, в скрытой вкладке опрос стоит), запрос — подсчёт по частичному индексу `notifications (user_id) WHERE read_at IS NULL` до 100. Когда счётчик вырос, обновляются список и приглашения; о новом приглашении — один неназойливый тост. Настройки писем — в настройках соискателя и на странице «Компания».
- **Решения модератора.** Уведомление пишется в той же транзакции, что решение, его строка журнала и изменения грейда или санкции (`moderation::decide`, `moderation::act`): не записалось уведомление — не случилось и решение (откат не проверяется тестами — §14). Модератор в уведомлении не назван. Компании — только её собственный объект (вакансия по названию), комментарий модератора и число подтверждённых жалоб: ни автора жалобы, ни её текста, а жалоба на приглашение не называет приглашение — оно ушло одному человеку, и название выдало бы автора (состав полей уведомлений компании — модульный тест `notify`, лента и страница доверия — black-box `moderation.spec.ts`). Подтверждённая жалоба приходит вместе с мерой, к которой привела (`vacancy_unpublished`, `invitations_frozen`), отдельным видом — только отклонённая. Мера меняет уровень доверия и квоту — в той же транзакции они записываются в `company_trust_seen`, иначе обход через пять минут сообщил бы о той же перемене ещё раз как `trust_changed`; естественное окончание заморозки по-прежнему приходит как `trust_changed`. Письмом все виды идут по умолчанию и отключаются по отдельности.

Тесты пользуются только публичными интерфейсами: сайт и API через Caddy (:8080), Mailpit как почта пользователей, демо-ATS и админка заглушки реестра ФСП как внешние системы. Отличие стека от демо — `deploy/compose.blackbox.yml`: сбор и пауза писем 3 с вместо 2 и 10 минут, без Keycloak и наблюдаемости. Сценарии — `docs/solution.md` §6.6.

Ограничения стека, вокруг которых устроен набор: вход — 10 попыток за 15 минут на IP + email (Caddy подставляет настоящий адрес клиента), поэтому сессии демо-аккаунтов логинятся один раз на слот воркера и переиспользуются; регистрация — 20 в час с адреса, поэтому новые аккаунты заводят только сценарии, которым они нужны (5–6 за прогон); каждый сценарий берёт своего засеянного соискателя и свою компанию, чтобы файлы шли параллельно; решения модератора окончательны, поэтому очередь разбирает один последовательный файл.

**Не покрыто ни тем ни другим:**

| Поведение | Почему |
|---|---|
| Откат приглашения, раскрытия контактов, решения модератора при сбое записи уведомления или события outbox | Нужна инъекция отказа в базу; атомарность держит одна транзакция в коде |
| Захват событий вебхука репликами (`FOR UPDATE SKIP LOCKED`), истёкшая аренда, одно напоминание при двух обходах | Блокировки и гонки базы; в стеке одна реплика |
| Горизонт опроса ATS по самой старой открытой пишущей транзакции | Нужна открытая транзакция в базе |
| Победа уникального индекса в гонке двух регистраций | Снаружи виден только итог — один 201 и один 409 `email_taken`, он проверен |
| Распространение поколения кеша на другие реплики через Valkey (≤ 250 мс) | Одна реплика в стеке; локальные правила поколения — модульные |
| Брошенный тест через 30 минут, 18-летие, очистка данных представителя через 30 дней после него, истечение приглашений и ссылок, удаление записей по сроку, напоминание за 48 ч | Время снаружи не подвинуть; правила проверены модульными тестами на заданном `now` |
| Перерасчёт векторов при смене модели эмбеддингов, повтор упавшего пакета через 5 с / 30 с / 2 мин | Нужна вторая модель или сбой посреди пакета; правила (`needs_embedding`, `retry_delay`) — модульные, а остановленный эмбеддер проверяет `make blackbox-degraded` |
| Выбор регулярного задания среди задач всех компаний | Порядок задаётся SQL `ORDER BY`; правило частоты (`due_for_assignment`) — модульное |
