# API

Полное описание методов - OpenAPI 3.1, который бэкенд генерирует из кода (utoipa): спецификация
`GET /api/v1/openapi.json`, Swagger UI - `/api/docs`; 131 операция на 111 путях. Там пути, роли,
схемы запросов и ответов, коды ошибок каждого метода и примеры тел. Копия спецификации -
`web/openapi.json`, из неё генерируются типы фронтенда (`make gen-api`).

В этом документе описано то, чего в спецификации нет, например общие соглашения, правила поведения, которые не видны
из схем, исходящие вебхуки, жизненные циклы статусов и заглушки внешних систем.

## Соглашения

### Версия и формат

- База - `/api/v1`. Breaking изменение - новая версия `/api/v2` рядом со старой; старая отдаёт заголовки `Deprecation` и `Sunset`.
- Формат - JSON, `snake_case`; даты - RFC 3339 UTC; деньги - целые рубли (`i64`); id - UUID v7.
- Длина текста считается в символах, не в байтах: лимит "до 4000 символов" одинаков для кириллицы и латиницы.

### Аутентификация

- **Браузер** - httpOnly cookie:
  - `fsp_at` - access JWT, 15 минут, путь `/`, `SameSite=Lax`;
  - `fsp_rt` - refresh, 30 дней, путь `/api/v1/auth`, `SameSite=Strict`;
  - `fsp_session` - без данных, 30 дней: по нему Next только решает, отправлять ли на `/login`;
  - `fsp_at_exp` - без `HttpOnly`, 30 дней: только срок действия access-токена (unix-секунды), самого токена в нём нет. По нему страница обновляет сессию до запроса, а не после его 401; выход и удаление аккаунта стирают и его.
- **API-клиенты и Swagger** - `Authorization: Bearer <jwt>` из ответа `POST /auth/login`.
- **ATS компании** - дерево `/api/v1/integrations/...` принимает только API-ключ `Authorization: Bearer fsp_live_...`: cookie и JWT туда не доходят, а ключ не открывает остальные пути. Ключ ограничен скоупами (`invitations:read`, `candidates:read`, `outcomes:write`, `needs:write`).
- **CSRF.** Изменяющий запрос с cookie и без `Authorization` должен прийти с `Origin` (при его отсутствии - `Referer`), равным `PUBLIC_URL` или начинающимся с `PUBLIC_URL/`; иначе 403 `csrf`.
- **Роли:** `candidate` (соискатель), `employer` (работодатель), `admin` - в интерфейсе "Модератор": регистрацией не выдаётся, в демо - `moderator@demo.fsp`. Роль задаёт префикс: `/candidate/*`, `/employer/*`, `/admin/*`; чужая роль - 403 `wrong_role`, без сессии - 401 `unauthorized`.

### Ошибки

RFC 9457 `application/problem+json`:

```json
{ "type": "about:blank", "title": "Смена грейда пока недоступна", "status": 409,
  "code": "grade_change_cooldown", "detail": "Следующая попытка - после 03.01.2027",
  "errors": { "field": ["сообщение"] } }
```

- `code` - стабильный машинный код, на него завязывается фронт; `title` и `detail` - для человека, на русском. Общие коды - `unauthorized`, `wrong_role`, `not_found`, `validation_failed`, `rate_limited`, `csrf`, `internal`. `errors` - только у 422.
- Запрос, который не удалось разобрать, - тоже problem+json (extractor'ы `crates/api/src/extract.rs`): `invalid_json` - 400, если тело не JSON, и 422, если JSON не по схеме (неизвестное значение enum, не тот тип, нет поля; что именно - в `detail`); `unsupported_media_type` - 415; `invalid_path` - 400, параметр пути не разбирается (например, не UUID); `invalid_query` - 400, нет обязательного query-параметра или он не разбирается; `payload_too_large` - 413; `invalid_body` - 400, тело не удалось дочитать.
- В OpenAPI эти ответы указаны у каждого метода, где они возможны, вместе с 401 `unauthorized` у методов с сессией, 403 `wrong_role` у методов кабинета одной роли и 403 `csrf` у изменяющих методов с сессией.
- У 409 `consent_required` есть расширения `document_id` и `document_kind` - документ, который нужно принять (`POST /me/consents`). У 409 `guardian_consent_required` те же поля указывают на `guardian_consent`, но принять его может только законный представитель по ссылке из письма.

Коды ответов:

| Код | Что означает |
|---|---|
| 200 / 201 / 204 | успех; 201 - создано |
| 202 | принято к обработке: событие реестра ФСП, повторная доставка вебхука |
| 303 | редиректы ФСП ID и ссылки отписки |
| 400 | неверный запрос |
| 401 | нет сессии или она истекла |
| 403 | нет прав |
| 404 | не найдено **или чужое** - существование чужого ресурса не раскрывается |
| 408 | запрос дольше 30 с |
| 409 | конфликт состояния: кулдаун, квота, повтор |
| 413 | тело больше лимита |
| 422 | ошибки полей |
| 429 | лимит запросов; `Retry-After` - сколько секунд осталось до сброса окна, то же словами в `detail` |
| 502 / 503 | реестр или ФСП ID недоступны или не настроены |

### Пагинация

- **Страницы со смещением** - `GET /vacancies` и `GET /employer/candidates`: `?limit=20&offset=0` -> `{ "items": [...], "total": 123 }`, `limit` до 100. Подборка - `limit` в фильтрах (по умолчанию 30, до 100).
- **Курсор** - у списков, которые растут: приглашения обеих сторон, отклики на вакансию, решения заданий, журнал доставок ATS, очереди и журнал модерации, лента уведомлений. Ответ `{items, next_cursor}`, следующая страница - `?cursor=<next_cursor>`; новые сверху. Курсор непрозрачен: keyset по времени и id (у ленты уведомлений - по id). `next_cursor: null` - страница последняя; курсор не из ответа - 400 `invalid_query`. `limit` - 1-100, по умолчанию 30; у журнала доставок - до 200, по умолчанию 50; у ленты уведомлений - 1-50, по умолчанию 20.
- **Опрос приглашений ATS** - тоже курсор, но по возрастанию и с задержкой в несколько секунд ("Интеграции ATS" ниже).
- Остальные списки отдаются массивом целиком.

### Размер тела

Превышение - 413 `payload_too_large`. Запрос больше 10 МиБ по `Content-Length` отсекается до хендлера.

| Запрос | Предел |
|---|---|
| По умолчанию | 256 КиБ |
| Резюме (`POST /candidate/resume`) | 10 МиБ |
| Фрагмент видео (`PUT /candidate/assessments/{id}/proctoring/chunks/{seq}`) | 1 МиБ |
| `POST /eval/pairs` | 8 МиБ |
| Событие реестра ФСП (`POST /fsp/registry/events`) | 16 КиБ |

### Создание

201 у вакансии, потребности, приглашения и сессии теста приходит с заголовком `Location` - путь, по которому созданное читается (`/api/v1/employer/vacancies/{id}` и т. п.).

### Идемпотентность

- `POST /employer/invitations` и `POST /employer/vacancies` принимают заголовок `Idempotency-Key` - до 100 символов, уникален в пределах компании. Повтор - и одновременная отправка - с тем же ключом возвращает 200 и уже созданное. Ключ длиннее 100 символов - 422 (`idempotency_key`); у приглашения - также ключ, уже использованный для другого кандидата. Кабинет делает один ключ на открытую форму, поэтому двойной клик не создаёт дубль вакансии и не снижает квоту отметкой "дубль своей".
- `POST /integrations/needs` с `external_id` (id вакансии в ATS, уникален в компании) при повторе возвращает 200 и уже импортированную потребность.
- Жалоба (`POST /reports`) - одна открытая на человека и объект: повтор возвращает её же с 200 и `already_open: true` и в суточный лимит не идёт.
- Согласие (`POST /me/consents`) при действующей выдаче - 200 и та же выдача.
- Этап найма от ATS идемпотентен по паре "приглашение или отклик + этап": повтор - 200, обновляет причину и время.
- Событие реестра ФСП применяется один раз на `event_id`.
- Фрагмент видео с уже принятым `seq` - 204 без перезаписи.
- Двойной клик "Начать тест" - 409 `assessment_in_progress`, а не 500.

### Лимиты запросов

Превышение - 429 `rate_limited` с `Retry-After`.

| Тип запроса | Лимит |
|---|---|
| Регистрация | 20 в час с IP |
| Вход | 10 попыток за 15 минут на пару IP + email |
| Повтор письма подтверждения | 3 письма в час на адрес |
| Письмо законному представителю | 3 в час от соискателя, 5 в сутки на адрес |
| Жалобы | 20 в сутки от пользователя |
| Тестовое событие вебхука | 10 в минуту |
| API для ATS | 120 запросов в минуту на ключ |
| События реестра ФСП | 300 в минуту с адреса |
| `POST /eval/pairs` | 10 за 10 минут с IP |

### Кеширование

- По умолчанию `Cache-Control: private, no-store` - всё, что за cookie, токеном или API-ключом, и всё с ПДн.
- Публично: `GET /catalog`, `/catalog/skills`, `/consents/current` - `public, max-age=300, stale-while-revalidate=86400`; `GET /vacancies`, `/vacancies/{id}`, `/vacancies/{id}/similar` - `public, max-age=30, stale-while-revalidate=120`. У публичных ответов есть `ETag`, `If-None-Match` -> 304.
- `/guardian/consent`, `POST /eval/pairs`, `GET /catalog/test-plan` - `no-store`. Ошибки и ответы с `Set-Cookie` в публичных группах - `no-store`; 401 - `private, no-cache`, данных в нём нет (`docs/architecture.md`, раздел 12.1).
- Тело ответа, которое клиенту не нужно, всё равно прочитать или отменить (`res.body?.cancel()`): Chrome не завершает непрочитанный ответ с `no-store` и держит соединение.

### Служебные пути

Вне спецификации, без `/api/v1`:

| Путь | За что отвечает |
|---|---|
| `GET /healthz` | живость процесса |
| `GET /readyz` | готовность: 200 или 503 с телом `db=<bool> kv=<bool>`; без `VALKEY_URL` проверка kv всегда проходит (хранилище в памяти) |
| `GET /metrics` | Prometheus; Caddy наружу не отдаёт |
| `GET /api/docs` | Swagger UI |

## Правила по разделам

### Регистрация и аккаунт

- Все обязательные для роли документы передаются в `consents` при регистрации, иначе 422 `consents`. Работодатель передаёт `company_name` и подтверждает 18+ в форме. Соискатель передаёт `age`: `adult` или `minor` с датой рождения (14-17 лет на сегодня) и представителем, чья почта не совпадает со своей. Возраст пишется в `age_bracket` выданных согласий.
- Ссылка подтверждения почты живёт 24 часа. У соискателя 14-17 лет подтверждение почты отправляет письмо законному представителю.
- `POST /auth/resend-verification` отвечает 204 всегда - наличие адреса не раскрывается.
- Выход отзывает семейство refresh-токенов и кладёт access-токен в deny-list; без сессии - тоже 204.
- Согласие даётся только на действующую редакцию и только на документ своей роли (`applies_to`); `guardian_consent` даёт только представитель. Выдача пишет время, IP и User-Agent. Отзыв `pd_publication` или `pd_processing` скрывает профиль соискателя, `proctoring_video` - сразу удаляет видеозаписи.
- `GET /me/export` - все данные аккаунта JSON-вложением `fsp-talents-<дата>.json` (ст. 14 152-ФЗ): согласия с редакциями, IP и датами, профиль, тесты с итогами (без заданий, ответов и видео), приглашения, отклики, журнал доступа к контактам, ФСП, уведомления и отправленные письма.
- `DELETE /me` удаляет аккаунт и ПДн, у 14-17 лет - вместе с данными законного представителя, а также уведомления, письма и их настройки.

### Уведомления

- Лента - то, что видит колокольчик в кабинете; письма собираются из той же ленты. Текст собирается из полезной нагрузки при чтении; `link` - путь в кабинете.
- Счётчик непрочитанных - до 100 (значок показывает "99+"), один подсчёт по частичному индексу: рассчитан на опрос раз в 30 с.
- Открытие приглашения (`GET /candidate/invitations/{id}`, `/employer/invitations/{id}`) отмечает прочитанными уведомления о нём.
- В кабинете приходят все виды; письма включаются и выключаются по видам, по умолчанию включены все. Письмо, уже стоящее в очереди, при отправке пропускает выключенные виды.
- Отписка в один клик (RFC 8058): почтовый клиент шлёт `POST /notifications/unsubscribe` с `List-Unsubscribe=One-Click`, кнопка на странице отписки - тот же POST. Токен подписан HMAC-SHA256 (ключ выводится из `BIDX_KEY`) и называет аккаунт и вид письма или все. `GET` по той же ссылке ничего не отключает - её открывают и сканеры почты - и делает 303 на страницу с кнопкой.

Виды (`kind`):

- соискателю: `invitation_received`, `invitation_expiring` (за 48 ч до истечения, один раз), `invitation_withdrawn`, `hiring_stage`, `application_status` ("просмотрено" - только в кабинете), `assessment_result`, `guardian_decision`, решения модератора по тесту `result_confirmed`, `result_annulled`, `retest_ordered` (с комментарием; модератор не назван), `fsp_achievements` (реестр прислал изменения);
- компании: `invitation_accepted`, `invitation_declined`, `application_received`, `webhook_failing`, `trust_changed`, решения модератора `vacancy_unpublished`, `invitations_frozen` (с датой), `sanction_lifted` (вакансия возвращена или заморозка снята досрочно), `complaint_resolved` (жалоба не подтвердилась; кто жаловался - не сообщается, приглашение из жалобы не называется).

В письмах компании нет ФИО и контактов соискателя - только анонимный код; комментарий соискателя к отказу виден только в кабинете.

### Соискатель

- Профиль: нужен хотя бы один способ связи; телефон - 10-15 цифр (допустимы `+` в начале, пробелы, скобки, дефис); Telegram - ник из 5-32 латинских букв, цифр и `_`, можно с `@` или ссылкой `t.me/...`.
- Резюме (PDF до 10 МиБ) возвращает распознанные поля как черновик формы, в профиль они сами не попадают. Сразу сохраняются только навыки с источником `resume` (заменяют прежние) и запись о загрузке.
- `visible: true` в приватности требует действующих `pd_processing` и `pd_publication` (иначе 409 `consent_required`), а до 18 лет - ещё и `guardian_consent` (409 `guardian_consent_required`).
- Представитель: новое письмо гасит старые ссылки; после отказа или отзыва - новый запрос тому же человеку. `PUT /candidate/guardian` меняет представителя или адрес и сразу отправляет письмо.
- "Кто открывал ваши контакты" - компания (`company_name: null`, если она удалила аккаунт), время, основание и канал: `cabinet`, `api` или `webhook` (передано в ATS компании); до 500 записей. Сотрудник, IP и браузер в ответ не входят.
- Шаг онбординга - поле `candidate.onboarding_step` в `GET /me`: профиль -> опрос -> тест -> категория.
- Рынок категории считает, сколько компаний открывали профиль за 30 дней.

### Тест и категория

Политика смены грейда описана в разделе 5.4 `docs/architecture.md`; здесь - как она видна в API.

- `GET /candidate/category`: `available` - тесты, доступные сейчас (`ordered_retest` - пересдача, назначенная модератором, `camera_required` - только с камерой); `locked` - тесты с датой открытия `available_at` и причиной: `retry_blocked` - 30 дней после неудачной или брошенной попытки на этот грейд, неудачного повышения или аннулирования результата модератором; `grade_change_cooldown` - 90 дней от присвоения. `next_change_at` - когда станет возможна смена грейда, если сейчас нельзя ни вверх, ни вниз.
- Старт теста с `camera: true` требует id текущего документа `proctoring_video` - выдача согласия пишется тут же. Если модератор назначил пересдачу с видеозаписью, тест на этот грейд и выше начинается только с камерой (409 `camera_required`). Специализация должна совпадать с опросом или категорией.
- Текущее задание приходит без правильного ответа, с дедлайном. Ответ после дедлайна засчитывается неверным, и выдаётся следующее задание. Если 30 минут после дедлайна прошли без ответа, сессия закрывается как `expired`.
- Результат: `needs_review` - "требует подтверждения", пока модератор не решил; `review` - решение с комментарием; `recording_views` - когда модератор смотрел запись.

### Прокторинг

Устройство описано в разделе 5.6 `docs/architecture.md`.

- При `PROCTORING=off` загрузка и события отвечают 409 `proctoring_off`. Работодателю ни один из путей не доступен; в его DTO есть только `CandidateCard.proctoring` - отметка без id сессии и ссылок.
- Фрагменты видео - сырым телом до 1 МиБ, строго по порядку с 0, пока тест идёт и 60 с после; только своя сессия с выбранной камерой и действующим согласием. `Content-Type` первого фрагмента (`video/webm` или `video/mp4`) запоминается для воспроизведения, иное считается webm. Предел записи - 64 МиБ или 720 фрагментов.
- События браузера - до 50 за запрос и до 500 на сессию, лишние отбрасываются, записываются и без камеры.
- Запись отдаётся потоком: фрагменты расшифровываются по порядку, `Content-Length` известен заранее.

### ФСП

Привязка и синхронизация - `docs/solution.md`, раздел 7.

- `state` привязки - одноразовый, живёт 10 минут; `state`, PKCE S256 и `nonce` хранятся в `oidc_states`. Callback делает 303 на `/candidate/settings?fsp=linked` или `?fsp=error&reason=...` (`cancelled`, `expired`, `no_fsp_id`, `verification_failed`, `already_linked`, ...).
- `POST /fsp/link/dev` - привязка без Keycloak, только при `FSP_DEV_LINK=true` (иначе 404).
- Синхронизация пишет новый снимок достижений и навыки, которые они подтверждают (источник `fsp`, `docs/architecture.md`, раздел 7.4). Участника нет в реестре - пустой список. Отвязка удаляет снимок, навыки из ФСП и принятые события реестра.
- **События реестра** (`POST /fsp/registry/events`) - push вместо опроса: `{event_id, type: "achievements.changed", fsp_id, occurred_at}` с подписью `FSP-Signature: t=<unix>,v1=hex(HMAC-SHA256(FSP_REGISTRY_WEBHOOK_SECRET, t + "." + тело))` - как у исходящих вебхуков. `t` дальше 5 минут - 401 `signature_expired`, нет подписи или не совпала - 401 `signature_invalid`. Для привязанного участника - та же синхронизация, что `POST /fsp/sync`, и, если что-то изменилось, уведомление `fsp_achievements`. Ответ 202 без тела одинаков для применённого, неизменившегося, повторного события и незнакомого `fsp_id` - о нём ничего не сохраняется; другие `type` принимаются и игнорируются. 502 `fsp_unavailable` - реестр не отдал достижения, событие стоит доставить позже.

### Подбор и приглашения

- В объяснении подборки признак `text` ("Близость описаний") считается по смыслу - косинус эмбеддингов потребности и профиля, если векторы у обоих посчитаны, иначе по ключевым словам; `explanation_ru` говорит, как именно. Закреплённые кандидаты при уточнении фильтров сохраняются.
- Поиск по банку без `need_id` упорядочен по силе профиля и не учитывает `city`; с `need_id` - по соответствию потребности. `adults_only` ("Только 18+") отсекает соискателей 14-17 лет - это фильтр, не штраф.
- Анонимный профиль: `candidate.minor` - отметка "14-17 лет" без даты рождения; `candidate.result_confirmed` - модератор подтвердил тест, давший категорию. Скрытый соискатель - 404, если у компании с ним нет приглашения или отклика. Просмотр учитывается в статистике спроса соискателя.
- Контакты - только при принятом приглашении или отклике (иначе 403 `contacts_not_granted`); каждое открытие пишется в журнал доступа.
- Квота приглашений - по уровню доверия, 5-30 приглашений, созданных за 7 дней, включая отозванные. Вилка приглашения сверяется с рынком категории соискателя; отметка пишется в приглашение и не блокирует его.
- Списки приглашений: `status` - статусы через запятую (`sent,viewed` - "Ждут ответа"); `by_status` - сколько приглашений каждого статуса без учёта фильтра, для счётчиков вкладок; `outcomes` - этапы найма, которые отметила ATS компании.
- Первое открытие приглашения соискателем переводит его в `viewed`. Отказ с причиной `not_looking` закрывает статус поиска; комментарий к отказу - до 1000 символов. Принять приглашение до 18 лет можно только с действующим согласием представителя.

### Вакансии и отклики

- Каждое сохранение вакансии подписывает её текст; публикация пишет отметки антифейка (вилка, дубль своей, копия чужой) и не блокирует. `warnings` - отметки словами; `paraphrase_of_other` ("по смыслу похоже на вакансию другой компании", без её названия) появляется через несколько секунд после публикации, когда посчитан вектор текста, и квоту не снижает.
- Вакансию, снятую модератором (`unpublished_by_moderator_at`), можно править, но не опубликовать (409 `vacancy_unpublished`).
- "Похожие вакансии": `method: meaning` - ближайшие опубликованные по косинусу эмбеддингов, сначала той же специализации; `skills` - эмбеддингов нет (выключены или вектор ещё не посчитан): той же специализации по доле общих навыков. `company_verified_domain` в вакансии и приглашении - отметка "Домен подтверждён".
- Отклик открывает компании контакты соискателя, поэтому до 18 лет он возможен только с действующим согласием представителя. Компания ставит статус `viewed` / `accepted` / `rejected` в любом порядке, пока соискатель не отозвал отклик.

### Доверие, антифейк и жалобы

Сигналы не блокируют действия: предупреждают работодателя, меняют уровень доверия и квоту, попадают в модерацию (`docs/architecture.md`, раздел 11.1).

- Квота за 7 дней = база + бонусы + штрафы; при заморозке - 0 до `frozen_until`. `GET /employer/trust` перепроверяет домен и показывает решения модератора о компании без автора жалобы.
- Проверка вилки: рынок категории - медиана и 90-й перцентиль ожиданий, если кандидатов не меньше 5, - по тем же соискателям, что карточки категорий: опубликованные (14-17 лет - с согласием представителя), поиск не закрыт.
- Похожие свои вакансии - сходство от 0,6; чужие не показываются.
- Жалоба открыта, пока модератор не решит: отклонённая перестаёт снижать квоту компании, подтверждённая считается свои 90 дней.

### Модерация

Кабинет модератора - `docs/architecture.md`, разделы 5.7, 11.1.

- Комментарий к решению или действию обязателен, до 2000 символов. Каждое решение, действие и просмотр записи пишется в журнал `moderation_actions` в той же транзакции.
- Очередь тестов - старые сверху; `filter`: `needs_review` (по умолчанию: "требует подтверждения" и без решения), `remarks` (уходы, вставки, выход из полноэкранного режима, без решения), `video` (все с камерой). В карточке теста нет ФИО, контактов и email соискателя.
- Просмотр записи пишет строку `view_recording` до первого байта; `HEAD` только проверяет, что файлы есть, и просмотром не считается.
- Решение по тесту одно и окончательное. `confirm` снимает "требует подтверждения", работодатель видит `result_confirmed`. `annul` аннулирует присвоение: категория - по последнему действующему присвоению или никакая, навыки только из этого теста теряют источник `test`, грейд закрыт на 30 дней от решения. `retest` - то же плюс немедленная пересдача той же попытки, только с камерой. Соискатель получает уведомление в той же транзакции.
- Очередь антифейка упорядочена по времени попадания в очередь; кабинет группирует загруженное по компаниям. `view=sanctions` - снятые вакансии и замороженные компании.
- Действия антифейка: `dismiss` - отметка перестаёт снижать квоту, жалоба закрыта как необоснованная, компания уходит из очереди до нового сигнала; `unpublish` - вакансия закрыта без права публикации, жалобы на неё подтверждены; `freeze` - на 1-90 дней, квота 0, жалобы на компанию и её приглашения подтверждены; `restore` - вакансия снова опубликована (её отметки сняты) или заморозка снята. Компания получает уведомление в той же транзакции, а запомненные уровень доверия и квота обновляются - повторного `trust_changed` о том же не будет.
- Журнал: `subject` - id объекта, соискателя или компании либо код соискателя "K-XXXXXX" (регистр, пробелы и дефис не важны); незнакомый код - пустой журнал.

### Интеграции: кабинет работодателя

Устройство - `docs/architecture.md`, раздел 11.2. Без профиля компании - 409 `company_profile_required`.

- Вебхук: только https (http - для хостов из `WEBHOOK_DEV_HOSTS`), без логина в URL, не во внутреннюю или служебную сеть, хост должен находиться в DNS. Первое сохранение возвращает `secret` один раз; дальше меняется только адрес.
- Смена секрета: сутки события подписаны и новым, и прежним. Отключение стирает адрес и секрет и отменяет события из очереди.
- Журнал доставок хранит завершённые события 30 дней. "Отправить ещё раз" работает в любом статусе и ставит событие в очередь с новым суточным окном.
- API-ключи: до 10 действующих; `secret` показывается один раз при создании; отозванный ключ перестаёт работать сразу.

### Интеграции ATS

Ошибки ключа: 401 `api_key_required` (нет ключа или это не `fsp_live_...`), 401 `api_key_invalid` (не найден или отозван), 403 `insufficient_scope`.

- **Опрос приглашений** вместо вебхука: приглашения, чей статус изменился после курсора, по возрастанию. `cursor` - непрозрачная позиция "время изменения + id"; пустая страница возвращает тот же курсор, полная (`limit` строк) значит, что ждут ещё. Изменения последних секунд (`ATS_POLL_LAG_SECS`, по умолчанию 5) и транзакций, которые ещё пишут, придут следующим вызовом - изменение, которое сохраняется прямо во время опроса, не перепрыгивается (`docs/architecture.md`, раздел 11.2). Прежний `since` (RFC 3339) работает как курсор "после этого момента", `next_since` - время последней строки; новым клиентам - `cursor`.
- До принятия соискатель в приглашении - только код и категория; после - ещё `id` и `contacts_available: true`. Полный профиль и PDF - только при принятом приглашении или отклике соискателя этой компании, иначе 404; каждый вызов пишется в журнал доступа (`channel: api`).
- Этап найма: `at` не позже чем через 5 минут и не старше года, причина до 500 символов; приглашение должно быть принято, отклик - не отозван.
- Импорт вакансии: текст до 20 000 символов разбирается в потребность; подборка строится при открытии `shortlist_url`.

### Согласие законного представителя

Публичная страница `/guardian/confirm?token=...` - из письма представителю соискателя 14-17 лет. Токен - 32 случайных байта, в базе только SHA-256. В письме две ссылки: **ответ** (одноразовая, 7 дней) и **отзыв** (пока согласие действует). `grant` и `decline` - по ссылке ответа, `revoke` - по ссылке отзыва; до ответа ссылка отзыва работает как `decline`. `grant` пишет выдачу `guardian_consent` с IP, User-Agent и временем представителя; `decline` и `revoke` скрывают профиль. Если участнику уже 18 (`participant_adult: true`), действий нет.

### Валидация

Проверка подбора на своём наборе "вакансия - кандидат" (`docs/solution.md`, раздел 6.4) - та же логика, что у `validate pairs` (`matching::pairs`); базу не трогает и ничего не сохраняет. Пределы: 200 вакансий, 5 000 кандидатов, 100 000 оценок, тексты до 20 000 символов, `k` - 1-20. Близость описаний - по смыслу (эмбеддинги локальной модели), если в наборе не больше 300 текстов и эмбеддер отвечает не дольше 60 с, иначе по ключевым словам; `text: {by_meaning, model, fallback}` в отчёте говорит, как посчитано и почему.

## Вебхуки (исходящие)

`POST` на адрес компании, тело - схема `WebhookEvent` в OpenAPI: `{id, type, created_at, company_id, data}`.

- **Заголовки:** `FSP-Event-Id` (= `id` для идемпотентности получателя, доставка "хотя бы один раз"), `FSP-Event-Type`, `FSP-Signature: t=<unix>,v1=<hex>[,v1=<hex>]`, где `v1 = HMAC-SHA256(secret, t + "." + тело)`; второй `v1` - прежним секретом в первые сутки после смены. Также `Content-Type: application/json`, `User-Agent: FSP-Talents-Webhooks/1.0`.
- **Получатель** отклоняет `t`, отличающееся от его часов больше чем на 5 минут.
- **Доставка:** таймаут соединения 5 с, ответа - 10 с; ответ 2xx - доставлено, редиректы не выполняются. Иначе повтор через 1 мин, 5 мин, 30 мин, 2 ч, 12 ч, пока очередной укладывается в 24 ч от создания, затем `failed` - у неотвечающего адреса после шестой попытки, ≈ 14,6 ч.
- Событие пишется, только если у компании в этот момент есть вебхук; позже ничего не досылается. `invitation.expired` появляется лениво - при следующем чтении приглашений.

| Событие | Ивент | Соискатель в `data.candidate` |
|---|---|---|
| `invitation.sent` / `.viewed` / `.declined` / `.expired` / `.withdrawn` | смена статуса приглашения | код и категория; у `declined` - `invitation.decline_reason` и комментарий |
| `invitation.accepted` | соискатель принял | + `id` и `disclosed`: ФИО, телефон, Telegram, email, основание, ссылки на профиль и PDF |
| `application.created` / `application.status_changed` | отклик создан или сменил статус | + `id` и `disclosed` (кроме отозванного) |
| `contacts.opened` | сотрудник открыл контакты в кабинете | код, категория, `id`; основание и время - полями `data` (`basis`, `basis_id`, `opened_at`), без контактов |
| `integration.test` | кнопка "Тестовое событие" | - |

## Статусы

**Приглашение:** `sent` -> `viewed` -> `accepted` | `declined`; из `sent`/`viewed` -> `expired` (14 дней) | `withdrawn`.

**Отклик:** `sent` -> `viewed` -> `accepted` | `rejected`; соискатель может отозвать (`withdrawn`) до решения.

**Сессия теста:** `in_progress` -> `passed` | `failed` | `expired` (30 минут после дедлайна текущего задания без ответа; проверяется лениво - при старте теста, чтении истории, категории и текущего задания, при ответе; `finished_at` - дедлайн + 30 минут). `expired` - брошенный тест: в правилах смены грейда он считается неудачной попыткой на свой грейд.

**Решение модератора по тесту** (`review.decision`): нет -> `confirm` | `annul` | `retest`, одно и окончательное. `annul` и `retest` аннулируют присвоение грейда; сама сессия остаётся `passed`, в правилах смены грейда она - неудачная попытка с моментом решения.

**Жалоба:** открыта -> закрыта модератором с решением `dismissed` (не подтвердилась) | `vacancy_unpublished` | `invitations_frozen` (подтвердилась).

**Согласие представителя** (`state`): `not_sent` (соискатель ещё не подтвердил почту) -> `pending` -> `granted` | `declined`; из `pending` -> `expired` (ссылка ответа старше 7 дней, письмо можно повторить); `granted` -> `revoked`.

**Видеозапись теста** (`proctoring.status`): `recording`, пока тест идёт -> `recorded` | `interrupted` (может появиться и во время теста - после `camera_lost` или `recording_failed`); без камеры - `declined`. После удаления файлов (срок хранения, отзыв согласия) статус сохраняется, `purged: true`.

Правка живёт в памяти процесса: после перезапуска заглушка снова отдаёт `data/participants.json`.
