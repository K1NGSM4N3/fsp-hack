# ФСП Таланты — платформа подбора ИТ-специалистов с подтверждённой категорией

**Хакатон «Лидеры цифровой трансформации 2026», спецтрек Федерации спортивного программирования России.**

Репозиторий: https://github.com/K1NGSM4N3/fsp-hack · Swagger UI развёрнутого решения: `/api/docs` · Отчёты валидации: `docs/validation/`

## Коротко о решении

Работодатель не ждёт откликов, а сам выходит на кандидата. Кандидаты разложены по **категориям** — специализация × грейд, — и категорию даёт только **адаптивный тест**, а не резюме. Внутри категории выше стоят те, у кого сильнее результат теста, подтверждены навыки и есть достижения ФСП. Работодатель описывает потребность, получает **объяснённую подборку** и отправляет **приглашение с обязательной зарплатной вилкой**. Кандидат видит условия до начала общения, а его контакты открываются работодателю только после согласия.

Что отличает решение:

1. **Тест, который бесполезно сливать.** Задания — параметрические шаблоны: у каждого кандидата свои числа, код и ответы, а ответ вычисляется генератором. Сложность сопоставима, потому что шаблоны откалиброваны по IRT и все кандидаты измеряются на одной шкале. В симуляции утечки у фиксированного теста при 50 % слитых ответов проходят 99,9 % слабых кандидатов, у нашего — 9–10 %, как и без утечки (§6.2).
2. **Механика контакта «работодатель → кандидат».** Анонимная карточка, объяснение попадания, вилка в первом сообщении, квота приглашений против спама, причины отказов обратно работодателю, статистика спроса кандидату (§5).
3. **Измеримое качество.** Собственная процедура валидации на синтетике со скрытой «истиной»: доля релевантных в топ-10 — 0,94 против 0,43 у поиска по ключевым словам резюме; итоговый грейд совпадает с истинным в 87 % случаев, при пересдаче — κ = 0,74 (§6).
4. **ФСП ID на Keycloak уже сейчас.** Привязка через OIDC + PKCE к заглушке ФСП ID на настоящем Keycloak 26, достижения из реестра влияют на ранжирование, кандидат без истории ФСП не штрафуется (§7).
5. **Видеозапись теста — по согласию и без потери анонимности.** Камера предлагается перед тестом, запись шифруется и хранится 90 дней; кандидат видит свою запись, работодатель — только отметку «Тест с видеозаписью» и число уходов со вкладки (§4.7, §8.2).

Frontend — Next.js (App Router, TypeScript) с клиентом, сгенерированным из OpenAPI. Права проверяет только API.

Данные: PostgreSQL — пользователи (email и ФИО зашифрованы), профили, навыки с источником (заявлен / из резюме / подтверждён тестом / ФСП), сессии тестов (хранятся только ссылки на экземпляры заданий), история грейдов, потребности и сохранённые подборки, приглашения и их история, журнал доступа к контактам, согласия.

## 4. Механика тестирования

### 4.1. Идея

Единый набор заданий утекает; генерация нейросетью «под каждого» не гарантирует сопоставимую сложность. Мы разделили две задачи:

- **Неповторимость** даёт генератор: шаблон задания по случайному `seed` выдаёт новый экземпляр — другие числа, код, имена, порядок и набор вариантов. Правильный ответ **вычисляется** генератором (мини-симулятор event loop JavaScript, расчёт подсети, выполнение SQL на сгенерированной таблице и т. п.), а не хранится.
- **Сопоставимость** даёт калибровка: у каждого уровня шаблона есть параметры модели IRT — дискриминативность `a`, сложность `b`, угадывание `c`. Способность всех кандидатов измеряется на общей шкале θ, поэтому разные задания дают сравнимый результат.

Сложность внутри шаблона задают «радикалы» (например, число асинхронных задач в event loop), а «инциденталы» (числа, имена, порядок) меняются без влияния на сложность.

### 4.2. Банк заданий

62 шаблона: 52 вычислительных генератора и 10 вариативных пулов (5–7 формулировок, 3–4 равноправных правильных ответа и 7–10 дистракторов на каждый вопрос). У каждого шаблона 1–3 уровня сложности, b ≈ −1,4…+1,4. Каждый уровень каждого шаблона даёт не менее 1961 различимого экземпляра на 2000 случайных `seed`; это закреплено тестом.

| Специализация | Шаблонов | Тем | Примеры |
|:----------------|:-----------|:------|:----------------------------------------------------------------------|
| Бэкенд | 24 | 10 | изменяемый аргумент по умолчанию в Python, порядок `defer` в Go, выбор индекса, token bucket, LRU, аномалии изоляции, SQL `GROUP BY / HAVING` |
| Фронтенд | 15 | 6 | порядок вывода в event loop, замыкания в цикле, приведение типов, специфичность CSS, box model, батчинг состояния React |
| DevOps | 18 | 10 | кэш слоёв Docker, ресурсы Kubernetes, CIDR, `location` в nginx, cron, права Linux, `increase()` в Prometheus, бюджет ошибок |
| QA | 18 | 8 | граничные значения, классы эквивалентности, pairwise, диаграммы состояний, таблицы решений, проверки API |
| ML | 18 | 8 | метрики по матрице ошибок, теорема Байеса, градиентный шаг, k-means, `groupby` в pandas, формы массивов NumPy |
| Безопасность | 15 | 8 | класс уязвимости во фрагменте кода, энтропия пароля, XOR-шифр, Base64, обход фильтров, правила межсетевого экрана |

Типы ответа: выбор одного, выбор нескольких, число, текст. Задания и интерфейс — на русском, код — на соответствующем языке.

### 4.3. Адаптивный тест

| Параметр | Значение |
|:---------------|:----------------------------------------------------------------------|
| Модель | 3PL; `c` = 1/k для выбора из k вариантов, 0 для числового и текстового ответа |
| Оценка θ | Апостериорное среднее (EAP), сетка из 81 точки на [−4; 4], априорное N(порог заявленного грейда; 1) |
| Выбор задания | Максимум информации Фишера в текущей θ, случайный выбор среди пяти лучших (контроль экспозиции), квоты по темам, без повторов шаблона |
| Остановка | Не менее 8 и не более 20 заданий; стоп, когда 95-процентный интервал по θ не содержит порог заявленного грейда |
| Решение | θ̂ ≥ порога → тест сдан |
| «Уверенно сдал» | Измеренный грейд выше заявленного или P(θ ≥ следующего порога) ≥ 0,9 → предлагается дотест на грейд выше |
| Время | Лимит на задание (60–180 с), просроченный ответ засчитывается как неверный |
| Аномалии | Статистика person-fit `l_z` («верно на трудных, неверно на лёгких», `l_z < −2`); вместе с событиями видеозаписи (уход со вкладки, вставка текста) результат помечается «требует подтверждения» — §4.7 |

Стек кандидата из опроса повышает приоритет шаблонов с совпадающими навыками, но шкала и пороги остаются общими. Навыки из правильно решённых заданий получают отметку «подтверждён тестом».

### 4.4. Почему тест устойчив к распространению заданий

| Что утекло | Что даёт утечка |
|:---------------------------------------------------|:----------------------------------------------------------------------|
| Конкретный экземпляр с ответом | Практически ничего: следующий кандидат получит другой `seed`, а значит другой код и другой ответ |
| Шаблон («тут спрашивают порядок вывода event loop») | Понимание, как решать такой класс задач, — ровно тот навык, который мы измеряем |
| Весь банк шаблонов | Ответы всё равно нужно вычислить, а на каждое задание действует лимит времени |

Количественная проверка — §6.2: даже при базе из ~42 тыс. слитых экземпляров совпадения встречаются в 0,02–0,05 % заданий, и доля прошедших слабых кандидатов не растёт (9–10 %), тогда как у фиксированного теста — до 100 %.

**Роль нейросетей:** только офлайн — предложить новый шаблон, который проходит ревью и пробную калибровку (показывается кандидатам без влияния на оценку) до попадания в рабочий банк. Сопоставимость обеспечивает калибровка, а не генерация.

### 4.5. Правила смены грейда

- **Первичное размещение.** Кандидат выбирает грейд и проходит тест. Не сдал — сразу может пройти тест на грейд ниже; повтор того же или более высокого грейда — через 30 дней (иначе тест можно было бы перебирать). Не сдал Junior — пересдача через 30 дней, категории пока нет.
- **Уверенно сдал** — один раз сразу предлагается дотест на грейд выше.
- **После присвоения** смена грейда вверх или вниз — не чаще раза в 90 дней (настраивается). Неудачная попытка повышения не понижает грейд; следующая — через 30 дней.
- Кандидат видит текущую категорию, историю опросов, тестов и присвоений, доступные попытки и дату, когда откроется смена грейда.

### 4.6. Как тест строится от вакансии

`GET /api/v1/catalog/test-plan` и `GET /api/v1/employer/needs/{id}/test-plan` показывают по описанию вакансии: целевой порог θ, темы, шаблоны, которые получат приоритет из-за стека вакансии, и примеры заданий для двух разных кандидатов. Например, для «Middle Go-разработчик: PostgreSQL, Kafka» приоритет получают `sql.group_by_having`, `sql.left_join_rows`, `go.defer_order`, `db.index_choice`, `db.isolation_anomaly`. Кандидаты А и Б получают одни и те же шаблоны и уровни, но разные запросы и данные — `WHERE o.amount > 600` у одного и `> 750` у другого.

### 4.7. Видеозапись теста и журнал событий

Это наше дополнение: ТЗ прокторинга не требует. Цель — подтвердить, что тест пройден самостоятельно, не нарушив приватность и не мешая отвечать. Режим задаётся переменной `PROCTORING=optional|off`; по умолчанию камера предлагается, но не обязательна.

**Перед тестом** кандидат видит шаг «Видеозапись во время теста»: предпросмотр камеры и три коротких пункта — что записываем (только видео с камеры, без звука и без экрана, в низком качестве), кто увидит (сам кандидат и администратор при разборе спора; работодатель — только отметку) и сколько храним (90 дней в зашифрованном виде). Галочка согласия — отдельный версионированный документ в общей системе согласий. Две кнопки: «Начать с видеозаписью» и «Продолжить без камеры». Без камеры тест засчитывается так же, у результата отметка «без видеозаписи».

**Во время теста** браузер записывает видео 320×240 с низким битрейтом и каждые 10 секунд отправляет фрагмент на сервер; в углу — индикатор «Идёт запись» с миниатюрой камеры. Отдельно, с камерой и без, отмечаются события: вкладка скрыта, окно потеряло фокус, выход из полноэкранного режима (его предлагаем, но не навязываем), вставка текста в поле ответа, камера отключилась, запись остановилась. Отправка фоновая и с повторами; любой сбой превращается в «запись прервалась», тест при этом продолжается.

**Итог** — сводка с одним из статусов «с видеозаписью», «без видеозаписи», «запись прервалась» и числом событий каждого типа. Она пересчитывается из сохранённых данных при каждом чтении, поэтому учитывает последний фрагмент, который рекордер отдаёт уже после последнего ответа (сервер принимает его ещё 60 секунд).

**«Требует подтверждения».** Ни флаг person-fit, ни уход со вкладки по отдельности не доказывают помощь со стороны: порог `l_z < −2` срабатывает примерно у 2 % честных кандидатов, а переключить вкладку может любой. Поэтому отметка ставится, только когда аномальный шаблон ответов совпал с уходами со вкладки, вставкой текста или выходом из полноэкранного режима. Грейд автоматически не меняется: отметку видят кандидат и администратор, который может посмотреть запись.

| Кто | Что видит |
|:--------------|:----------------------------------------------------------------------|
| Кандидат | Сводку в результате и в истории тестов, свою запись, дату её удаления и ровно ту отметку, которую видят компании |
| Работодатель | Только отметку в анонимной карточке и профиле: «Тест с видеозаписью», «Тест без видеозаписи», «Запись прервалась», «Есть замечания: 2 ухода со вкладки». Видео недоступно ни до, ни после принятия приглашения |
| Администратор | Журнал событий и запись любой сессии — для разбора спорного результата |

## 5. Механика подбора и категоризация

### 5.1. Категоризация

Категория присваивается только по результату теста: сданный тест на заявленный грейд → категория «специализация · грейд». Самоописание и резюме влияют лишь на вторичные признаки (стек, ожидания) и никогда не определяют категорию. Кандидат без категории в поиске не участвует.

### 5.2. Сценарий выхода на контакт

1. Работодатель описывает потребность — формой или вставкой текста вакансии; система распознаёт специализацию, грейд, обязательные и желательные навыки, вилку, формат.
2. Система показывает **рекомендованные категории**: сколько кандидатов, сколько с ФСП, медианные ожидания, насколько категория покрывает стек.
3. **Подборка** — анонимные карточки: категория, сила результата теста, навыки с отметкой «подтверждён тестом / ФСП / заявлен», достижения ФСП, опыт (названия компаний — по желанию кандидата), ожидания. Без имени и контактов.
4. **Объяснение** у каждого кандидата: балл 0–100, разложение по признакам, причины («Все обязательные навыки: Go, PostgreSQL, Kafka; 1 подтверждён тестом», «Результат теста выше 71 % диапазона грейда Middle», «ФСП: Мастер спорта по продуктовому программированию, 2023») и пробелы («Нет обязательного навыка: Kubernetes», «Вместо PostgreSQL — близкий навык MySQL», «Навык Docker только заявлен»).
5. **Приглашение**: что предлагаем, сообщение, вилка «от–до» (обязательно), формат, способ связи с компанией; можно без вакансии.
6. Кандидат видит условия до общения и принимает или отклоняет с причиной (зарплата, стек, формат, компания, не ищу работу).
7. После принятия работодатель получает контакты; каждое обращение к контактам записывается в журнал.

### 5.3. Ранжирование

Жёсткие фильтры: кандидат видим и открыт к предложениям, категория нужной специализации, грейд из запрошенных (или соседний, если разрешено), формат и город совместимы.

Балл — взвешенная сумма признаков из [0; 1], веса подобраны на валидации (§6.3):

| Признак | Вес | Расчёт |
|:-------------------|:------|:----------------------------------------------------------------------|
| Обязательные навыки | 0,41 | Среднее по навыкам потребности: близость × доверие к источнику (тест / ФСП — 1,0; резюме — 0,7; заявлен — 0,5) |
| Грейд | 0,15 | 1,0 — точное совпадение, 0,6 — на грейд выше, 0,5 — на грейд ниже |
| Результат теста | 0,10 | Положение θ внутри диапазона грейда |
| Достижения ФСП | 0,10 | ФСП-скор (§7.3) |
| Желательные навыки | 0,08 | Как обязательные |
| Зарплата | 0,07 | 1,0, если ожидания в вилке; линейно до 0 при превышении на 30 % |
| Актуальность | 0,05 | exp(−дней с последней активности / 60): тест, задание, ответ на приглашение |
| Близость текстов | 0,04 | Полнотекстовая релевантность «о себе» описанию потребности (русская морфология) |

Признаки без данных (нет желательных навыков, нет описания) выпадают, веса перенормируются. Без потребности — при просмотре категории — кандидаты упорядочены по силе профиля: 0,6 · тест + 0,25 · ФСП + 0,15 · актуальность.

Подбор 10 000 кандидатов с объяснением топ-20 занимает около 0,3 мс; в ранжирующем цикле нет аллокаций, тексты объяснений собираются только для итоговых кандидатов.

### 5.4. Уточнение без потери подборки

Подборка хранится. При уточнении фильтров она пересчитывается, но закреплённые кандидаты остаются (с пометкой, если не проходят новые фильтры), скрытые не возвращаются, а новые помечаются как «новые».

### 5.5. Чем это отличается от отклика на вакансию

- Инициатива у работодателя, который ищет по подтверждённым тестом категориям, а не по ключевым словам.
- Условия — в первом же сообщении: кандидат решает, тратить ли время.
- **Квота**: не более 30 приглашений компании за 7 дней и одно действующее приглашение на пару «компания–кандидат». Работодатель выбирает точечно, кандидат не тонет в спаме.
- Приглашение живёт 14 дней. Работодатель видит воронку и агрегированные причины отказов, кандидат — анонимную статистику спроса в своей категории: сколько компаний смотрели профиль, медианная вилка приглашений.
- Классический отклик остаётся дополнительным путём: контакты раскрываются и при собственном отклике.

## 6. Процедура валидации и результаты

Валидация — отдельный исполняемый модуль `crates/validate` (`make validate`), который вызывает **те же крейты**, что и API, и пишет отчёты в `docs/validation/`. Данных и разметки организаторы не дают, поэтому используется синтетика со скрытой «истиной».

### 6.1. Тестирование: точность и стабильность

Каждая сессия — настоящий движок; синтетические только ответы: вероятность верного ответа по 3PL при истинной θ ~ N(0; 1). 400 человек на специализацию, процедура как в API (заявленный грейд → при провале грейд ниже). Пересдача — вторая независимая процедура с другими заданиями.

| Сценарий | Решение «выше/ниже порога» верно | Итоговый грейд = истинный | Отклонение ≤ 1 грейда | Совпадение при пересдаче | κ Коэна | RMSE θ | Заданий |
|:----------------------------------------------|:-----------------------------------|:----------------------------|:------------------------|:---------------------------|:----------|:---------|:----------|
| Честная заявка, точная калибровка | 87,7 % | 87,0 % | 100 % | 81,1 % | 0,74 | 0,35 | 13,6 |
| 20 % завышают, 10 % занижают грейд | 87,7 % | 80,2 % | 99,2 % | 80,1 % | 0,72 | 0,35 | 13,4 |
| Ошибка калибровки заданий (a ×0,8…1,2, b ±0,3) | 87,1 % | 86,2 % | 100 % | 80,2 % | 0,72 | 0,35 | 13,6 |

Ошибки только «вниз» и только у границы грейда: тест на заявленный грейд не повышает принудительно, а пограничный кандидат может пересдать на грейд выше. Неточная калибровка почти не ухудшает результат.

**Дискриминативность:** точечно-бисериальная корреляция верного ответа с истинной θ — в среднем 0,30, у 94 % шаблонов ≥ 0,2. Самые слабые шаблоны выводятся в отчёт как кандидаты на перекалибровку. Низкая корреляция у шаблона с несколькими уровнями может быть артефактом смешения уровней: адаптивный тест показывает трудный уровень более сильным кандидатам, поэтому внутри уровня корреляция выше, чем по шаблону в целом (так было с `go.defer_order`: 0,30 / 0,21 / 0,50 по уровням при 0,13 в сумме; уровень перекалиброван).

### 6.2. Тестирование: устойчивость к утечке

Слабые кандидаты (истинная θ от −0,9 до −0,1, ниже порога Middle) сдают тест на Middle.

| Утекло | Фиксированный тест: прошли | Наш тест: прошли |
|:-------------|:-----------------------------|:-------------------|
| 0 % | 9,4 % | 9,7 % |
| 25 % ответов | 65,2 % | 9,6 % |
| 50 % ответов | 99,9 % | 9,3 % |
| 100 % ответов | 100 % | 10,4 % |

Фиксированный тест — публичная форма из 15 самых информативных заданий. Для нашего теста «утечка» — база из всех экземпляров, показанных в 600 предыдущих сессиях на специализацию (~42 тыс. экземпляров); слабый кандидат отвечает верно, если ему выпал экземпляр из базы. Совпадения с базой случаются в 0,02–0,05 % заданий, поэтому утечка не даёт преимущества. Статистика person-fit ловит 11–12 % «сливщиков» фиксированного теста при 0,9 % ложных срабатываний.

### 6.3. Подбор: доля релевантных в топе

2 400 синтетических кандидатов, 120 потребностей для подбора весов и 120 отложенных для оценки. У кандидата есть скрытая истина (реальные навыки и θ) и наблюдаемый профиль с шумом: ~18 % заявленных навыков приукрашены, ~15 % реальных не заявлены, категория — из теста с ошибкой измерения, часть навыков подтверждена тестом. Релевантность (0–3) считается по истине функцией, отличной от скоринга. Релевантным считается оценка ≥ 2.

| Ранжирование | Precision@10 | nDCG@10 | MRR |
|:---------------------------------------|:---------------|:-------------|:------|
| Наш подбор (веса после валидации) | 0,941 ± 0,017 | 0,835 ± 0,023 | 1,000 |
| Наш подбор, исходные веса | 0,888 ± 0,022 | 0,758 ± 0,027 | 0,986 |
| Ключевые слова резюме + заявленный стаж | 0,425 ± 0,030 | 0,356 ± 0,028 | 0,632 |
| Случайный порядок в специализации | 0,223 ± 0,025 | 0,173 ± 0,018 | 0,414 |

Абляции: без результата теста nDCG падает до 0,819, без графа близости навыков — до 0,829, только по навыкам — до 0,739. Исходные веса (обязательные навыки 0,30, тест 0,25) проигрывали; на трёх случайных сидах устойчиво лучшим оказался вариант с большим весом стека и грейда — он и принят.

### 6.4. Ограничения и экспертная проверка

Синтетическая «истина» задаётся командой, поэтому абсолютные цифры описывают поведение системы в заданных предпосылках, а не рынок. Сравнение с базовыми линиями и абляции от этого не зависят. Следующий шаг — экспертная разметка: 10–20 реальных вакансий партнёров ФСП, топ-20 выдачи каждой оценивают два эксперта по шкале 0–3, согласованность экспертов (κ) и Precision@10 считаются тем же модулем `validate`. Для тестов — пилот на участниках соревнований ФСП: сравнение грейда по тесту с разрядом и результатами соревнований, повторная сдача через неделю.

## 7. Интеграция с ФСП

### 7.1. Привязка ФСП ID

```
Кандидат ──▶ API /fsp/link/start ── state, PKCE, nonce ──▶ Keycloak realm fsp (ФСП ID)
                                                              │ вход участника
API /fsp/link/callback ◀── code ──────────────────────────────┘
   │  обмен code → id_token по обратному каналу, проверка подписи (JWKS), iss, aud, nonce
   │  claim fsp_id
   ▼
Реестр ФСП: GET /participants/{fsp_id}/achievements (Bearer)
   │
   ▼
Снимок достижений в профиле → ФСП-скор → ранжирование и карточка
```

- ФСП ID работает на Keycloak; совместимость — стандартный OpenID Connect, клиент `fsp-talent` с обязательным PKCE S256. Claim `fsp_id` — атрибут пользователя Keycloak.
- Один ФСП ID можно привязать только к одному профилю. Отвязка удаляет снимок достижений.
- Если реестр недоступен, привязка сохраняется, синхронизация повторяется позже.
- Для интеграции с реальным реестром достаточно заменить адрес реестра и выдать API клиентские учётные данные Keycloak (client credentials или token exchange).

### 7.2. Какие данные получаем

Для каждого достижения: тип (разряд или соревнование), дисциплина (алгоритмическое, продуктовое программирование, программирование систем ИБ, систем ИИ, робототехники, БАС), разряд (юношеский, III–I, КМС, МС), уровень соревнования (региональное, межрегиональное, всероссийское, международное), место (1–3, финалист, участник), команда, роль, дата, ссылка на протокол.

### 7.3. ФСП-скор

Вклад достижения = вес уровня × вес места (или вес разряда) × релевантность дисциплины специализации × затухание с периодом полураспада 2 года. Итог — «шумное ИЛИ»: 1 − Π(1 − vᵢ). Скор растёт с каждым достижением, но насыщается и не может перевесить тест и стек (вес в подборе — 0,10). Учитывается только высший разряд в дисциплине.

**Кандидат без истории ФСП** получает 0 без штрафа: в карточке нейтральное «Нет данных ФСП», отсутствие ФСП никогда не попадает в «пробелы». Кандидат может скрыть ФСП-данные — тогда они не участвуют и в ранжировании.

## 8. Безопасность и 152-ФЗ

### 8.1. Аутентификация

- Пароли — Argon2id (19 МиБ, t = 2, p = 1); при неизвестном email выполняется та же проверка, чтобы время ответа не раскрывало наличие аккаунта.
- Короткий access-токен (JWT EdDSA, 15 минут) и ротируемый refresh-токен (30 дней) в httpOnly-cookie; повторное использование старого refresh-токена отзывает всю цепочку. Выход заносит access-токен в deny-list.
- Защита от CSRF: изменяющие запросы с cookie принимаются только с собственного Origin.
- Ограничение частоты: вход, регистрация, повторные письма, приглашения, жалобы.

### 8.2. Персональные данные

- Email, ФИО и контакты кандидата хранятся зашифрованными (XChaCha20-Poly1305); поиск по email — через keyed-хеш (blind index).
- Версионированные согласия на обработку и публикацию с фиксацией времени, IP и User-Agent. Каждый документ знает, кому он адресован: обработка и соглашение — обеим ролям, публикация и видеозапись — только кандидату.
- **Публикация только с согласием.** Показать профиль в поиске можно лишь при действующих согласиях на обработку и на публикацию; иначе сервер отвечает 409 `consent_required` и называет документ, который нужно принять, — интерфейс тут же предлагает его текст. Отзыв любого из них сразу скрывает профиль. Дать согласие снова можно в настройках: принимается только действующая редакция документа, повторная выдача ничего не дублирует.
- **Двойная проверка в поиске.** Пул кандидатов для подборок, поиска по банку, статистики категорий, анонимного профиля и приглашений сам проверяет действующее согласие на публикацию — флага «видим» недостаточно. Сохранённая подборка перепроверяется при каждом показе, поэтому скрытый профиль исчезает из неё сразу, без пересборки.
- **Право на доступ (ст. 14).** Кнопка «Скачать мои данные» отдаёт JSON-файл со всем, что хранится об аккаунте: профиль, согласия с редакциями и датами, тесты с итогами (без самих заданий и ответов), история категории, приглашения, отклики, журнал доступа к контактам, сводки видеозаписи без видео. Работодатель получает свой аккаунт и данные компании.
- **Журнал доступа к контактам**: кто, когда, на каком основании. Кандидат видит его в настройках как «Кто открывал ваши контакты» — компания, время, основание (принятое приглашение или собственный отклик), без сотрудника и его IP.
- **Передача в ATS компании** — только после принятия приглашения или отклика и тем же путём, что и в кабинете; каждая передача видна кандидату в том же журнале. Дальше компания обрабатывает данные в своей ATS как самостоятельный оператор (§10.1).
- **Политика обработки персональных данных** (ст. 18.1) — публичная страница `/privacy`: состав данных, цели, основания, кому видны, сроки, cookies, права и как ими пользоваться в кабинете, действующие тексты согласий.
- Удаление аккаунта стирает персональные данные, связи обезличиваются.
- Хранение — на сервере в РФ.

**Видеозапись теста** (§4.7):

- **Согласие** — отдельный версионированный документ «Согласие на видеозапись во время теста», при регистрации не запрашивается. Его выдача фиксируется так же, как остальные: время, IP, User-Agent. Без согласия запись не начинается: сервер отклоняет старт теста с камерой, если не подтверждена текущая версия документа.
- **Что именно:** только изображение с камеры, без звука и содержимого экрана; запись не используется для распознавания лица и установления личности.
- **Шифрование.** Каждый 10-секундный фрагмент шифруется XChaCha20-Poly1305 тем же модулем, что и персональные данные, и привязывается к своей сессии и номеру: файл, перенесённый в чужую запись или на другое место, не расшифруется. Файлы лежат в отдельном каталоге (в Docker — отдельный том), в базе — только метаданные: выбор камеры, ссылка на согласие, номера и размеры фрагментов, события. Запись отдаётся потоком и расшифровывается по одному фрагменту.
- **Срок хранения** — 90 дней. Фоновая задача удаляет просроченные записи при старте сервера и каждые 6 часов; сводка и отметка остаются.
- **Отзыв согласия** в настройках сразу удаляет все записи кандидата; **удаление аккаунта** удаляет их вместе с остальными данными.
- **Лимиты:** фрагмент до 1 МиБ, запись до 64 МиБ, не больше 50 событий за запрос и 500 на тест.

### 8.3. Разграничение доступа

- Роли кандидата и работодателя проверяются на уровне маршрутов; кандидат видит только свои приглашения, отклики и тесты, чужие ресурсы возвращают 404.
- **Контакты закрыты типами.** Карточка кандидата для работодателя не содержит полей контактов. Контакты можно получить только из «основания доступа», которое выдаёт единственная функция: она проверяет принятое приглашение или отклик и пишет журнал.
- **Видео закрыто так же.** В карточке для работодателя есть только отметка о видеозаписи — статус и число замечаний, без идентификатора сессии и ссылок. Запись отдают два метода: кандидату — его собственная, администратору — любая, с записью в журнал. Для работодателя оба отвечают 403: анонимность сохраняется до принятия приглашения, а видео не раскрывается и после.

### 8.4. ГОСТ и сертифицированная криптография

Алгоритм хранится вместе с данными (строка хеша PHC, версия шифротекста), хеширование и шифрование — за интерфейсами. Переход на ГОСТ (PBKDF2-HMAC-Стрибог по Р 50.1.111-2016, «Кузнечик») и сертифицированное СКЗИ — это новая реализация интерфейса без изменения схемы данных; в MVP ГОСТ не используется, так как соответствие обеспечивает сертификация СКЗИ, а не сам алгоритм.

### 10.1. Интеграция с ATS работодателя

ТЗ относит интеграцию с внутренними ATS к концепциям. Мы сделали её рабочим универсальным слоем, через который подключается любая система подбора, умеющая принять HTTPS-запрос или опрашивать REST API. Нативные коннекторы к конкретным ATS — тонкие адаптеры поверх этого слоя, их план — в конце раздела. В демо-стенде компания `employer@demo.fsp` уже подключена к демо-ATS (`http://localhost:8082`): события о приглашениях приходят туда с подписью, а кнопки «Собеседование», «Оффер», «Нанят», «Отказ» возвращают этап кандидату.

**Как устроено**

```
кандидат принял приглашение
        │  одна транзакция PostgreSQL
        ▼
invitations.status = accepted
  + invitation_events + contact_access_log (канал webhook)
  + integration_events: invitation.accepted (тело зашифровано)
        │  диспетчер в каждой реплике API: FOR UPDATE SKIP LOCKED,
        │  аренда 60 с, подпись HMAC, DNS только в публичные адреса
        ▼
ATS работодателя ── API-ключ fsp_live_…, скоупы ──▶ /api/v1/integrations
    GET  /invitations       опрос вместо вебхука
    GET  /candidates/{id}   профиль и PDF после согласия (ContactGrant, журнал)
    POST /outcomes          собеседование, оффер, найм, отказ → кандидату
    POST /needs             текст вакансии → потребность и подборка
```

| Часть | Что делает |
|:----------------------|:----------------------------------------------------------------------|
| Outbox событий | Событие записывается в той же транзакции, что и смена статуса. Если запись не удалась, откатываются и статус, и запись в журнале доступа — состояние платформы и поток событий не расходятся |
| Диспетчер | Фоновая задача в каждой реплике API. Берёт до 16 готовых событий с `FOR UPDATE SKIP LOCKED` и сразу сдвигает время следующей попытки на 60 секунд: реплики не отправят одно событие дважды одновременно, а упавшая реплика его не потеряет. Повторы через 1 мин, 5 мин, 30 мин, 2 ч и 12 ч; через сутки событие помечается недоставленным |
| Вебхук компании | Один HTTPS-адрес на компанию. Секрет подписи показывается один раз; его можно сменить (сутки события подписаны обоими секретами) или отключить вебхук целиком |
| Журнал доставок | Каждая попытка: код ответа, задержка, ошибка. Кнопки «Отправить ещё раз» и «Тестовое событие» — в кабинете «Интеграции» |

| Этапы найма | ATS отмечает собеседование, оффер, найм или отказ. Кандидат видит «Компания отметила: собеседование» в приглашении или отклике, работодатель — этапы в воронке на главной |
| Импорт вакансий | Текст вакансии из ATS разбирается тем же разборщиком, что и форма потребности: специализация, грейды, стек, вилка, формат. В ответе — id потребности и ссылка на подборку |

**Безопасность**

- **Подпись.** Заголовок `FSP-Signature: t=<unix>,v1=<hex>`, где `v1 = HMAC-SHA256(секрет, t + "." + тело)`. Метка времени входит в подпись, а получатель отклоняет запросы старше 5 минут, поэтому перехваченное событие нельзя отправить повторно позже. Секрет хранится зашифрованным и привязан к компании.
- **Защита от SSRF.** Адрес компании — это ввод пользователя, и платформа не должна стать прокси во внутреннюю сеть. Принимаются только `https://` без логина в адресе, редиректы не выполняются. Адрес проверяется внутри DNS-резолвера HTTP-клиента при каждом соединении: все адреса имени должны быть публичными (не loopback, не частные сети, не link-local с 169.254.169.254, не CGNAT, не служебные диапазоны, включая IPv6 и IPv4 внутри IPv6). Поэтому имя, которое после проверки начали резолвить в 127.0.0.1 (DNS rebinding), всё равно не пройдёт. Исключение — хосты из `WEBHOOK_DEV_HOSTS`: в демо так подключён контейнер демо-ATS.
- **Ключи.** `fsp_live_` и 256 случайных бит. В базе только SHA-256 и видимый префикс: при такой энтропии медленный хеш не нужен, а по утёкшей базе ключ не восстановить. Ключ показывается один раз, отзывается мгновенно, у каждого видно время последнего запроса. Лимит — 120 запросов в минуту на ключ.
- **Скоупы и границы.** Ключ без `candidates:read` не получит профиль, без `outcomes:write` не отметит этап. Дерево `/api/v1/integrations` принимает только ключ — cookie и JWT туда не доходят, а с ключом не открыть ни один метод кабинета.

**152-ФЗ**

- **Что и когда уходит в ATS.** До принятия приглашения — только анонимный код, категория и данные самого приглашения: должность, вилка, формат, статус, причина отказа. ФИО, контакты и PDF-профиль попадают в событие только после того, как кандидат принял приглашение или сам откликнулся. Это то же основание, по которому компания видит контакты в кабинете, и в коде путь тот же: данные раскрываются только через `ContactGrant`. Видео теста, ответы на задания и данные других компаний не уходят никогда.
- **Каждая передача в журнале.** Кандидат видит в «Кто открывал ваши контакты» и открытие в кабинете, и передачу в ATS компании — с пометкой «передано в систему подбора компании».
- **Кто отвечает дальше.** Получив данные после согласия кандидата, компания обрабатывает их в своей ATS как самостоятельный оператор — для своего подбора, по своим правилам хранения. Об этом сказано в политике обработки `/privacy`. Отключение вебхука или отзыв ключа прекращает передачу; удалить уже переданное кандидат может, обратившись к компании.
- **Минимизация у нас.** Тело события в очереди зашифровано тем же XChaCha20-Poly1305, что и поля ПДн, с привязкой к id события. Завершённые события удаляются через 30 дней, а при удалении аккаунта кандидата его события удаляются сразу. Компания без вебхука событий не получает вовсе, значит и раскрытия нет.

**Этапы найма как разметка.** Главный пробел валидации подбора — нет экспертной разметки, кто из подборки на самом деле подошёл (§6.4). Этапы из ATS — это настоящие исходы найма по конкретным приглашениям: дошёл до собеседования, получил оффер, вышел на работу. Они хранятся вместе с приглашением, а оно связано с потребностью и подборкой, где у кандидата был свой балл. Накопив исходы, можно калибровать веса ранжирования на реальных данных, а не на синтетике: подбирать веса признаков так, чтобы нанятые оказывались выше в подборке.

**Нативные коннекторы.** Универсальный слой уже покрывает ATS, которые принимают вебхуки или умеют опрашивать REST. Нативный коннектор — отдельный воркер, который читает тот же outbox как внутренний вебхук и переводит события в API конкретной системы. Его настройки в кабинете: токен ATS (хранится зашифрованным), вакансия по умолчанию и таблица соответствия статусов компании нашим этапам. Сведения о Huntflow, «Потоке» и Talantix взяты из их опубликованной документации API; про E-Staff и Skillaz открытой спецификации мы не нашли, для них описан подход.

Источники: [Huntflow API v2](https://api.huntflow.ru/v2/docs) (спецификация `https://api.huntflow.ru/v2/openapi.json`), [публичное API «Потока» v3](https://api-doc.potok.io/public-api/index.html) и [описание на сайте](https://potok.io/features/otkrytoe-api-potok/), [документация API Talantix](https://api.talantix.ru/docs/) и [анонс API Talantix 2.0 на hh.ru](https://hh.ru/article/32514).

## 12. Сборка, развёртывание и запуск

### 12.1. Docker (рекомендуется)

Требования: Docker с Compose v2, 4 ГБ свободной памяти.

```sh
git clone https://github.com/K1NGSM4N3/fsp-hack && cd fsp-hack
cp .env.example .env
docker compose -f deploy/compose.yml --profile full up -d --build
```

| Что | Адрес |
|:--------------------|:------------------------------|
| Приложение | http://localhost:8080 |
| Swagger UI | http://localhost:8080/api/docs |
| Письма подтверждения | http://localhost:8025 |
| ФСП ID (Keycloak) | http://localhost:8081 |
| Демо-ATS работодателя | http://localhost:8082 |
| Grafana | http://localhost:3001 |

При первом старте API применяет миграции и заполняет демо-данные: 6 вымышленных компаний, 12 вакансий, 240 кандидатов с симулированными тестами, 15 из них с ФСП.

**Демо-доступы** (пароль `demo12345`): работодатель `employer@demo.fsp`, кандидат `candidate@demo.fsp`, кандидаты `cand1@demo.fsp`…, участники ФСП ID в Keycloak `fsp-000001`…`fsp-000010`.

### 12.2. Локальная разработка без Docker

Требования: Rust ≥ 1.85, Node.js ≥ 20, PostgreSQL ≥ 14. Либо `nix develop` — окружение со всеми инструментами.

```sh
make db       # база fsp_hack
make api      # API на :8000 (миграции при старте; ФСП ID — dev-привязкой)
make web      # интерфейс на :3000
make validate # отчёты валидации в docs/validation/
make test     # тесты; тесты БД создают временные базы в локальном PostgreSQL
```

Сборка не требует базы: запросы sqlx проверяются по метаданным из `.sqlx/`. После изменения SQL или миграций — `make db-prepare`.

### 12.3. Для VPS

Задать в `.env` публичные адреса (`PUBLIC_URL`, `KC_HOSTNAME`, `FSP_OIDC_ISSUER`, `FSP_OIDC_REDIRECT_URL`), включить `COOKIE_SECURE=true` (камера в браузере доступна только по HTTPS или на localhost; видеозапись отключается `PROCTORING=off`, файлы лежат в томе `proctoring-data`), сгенерировать новые ключи (`JWT_ED25519_SEED_B64`, `FIELD_ENC_KEY`, `BIDX_KEY` — по 32 байта в base64) сменить пароли Keycloak и Grafana и указать в `deploy/Caddyfile` домен вместо `:8080` — Caddy сам получит TLS-сертификат.
